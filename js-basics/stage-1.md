## СЛОЙ НУЛЕВОЙ. Без этого вообще нельзя начинать.

Это не повторение — это фундамент. Если что-то из этого звучит незнакомо, нужно вернуться к книге прежде чем двигаться дальше.

**Что такое переменная.** Переменная — это именованная ячейка памяти. Когда ты пишешь «const x равно пять», ты говоришь компьютеру: зарезервируй кусочек памяти, назови его x, положи туда число пять. Имя — это просто удобный способ обращаться к адресу в памяти.

**Что такое тип данных.** Одни и те же байты в памяти можно интерпретировать по-разному. Байты «01000001» — это число 65, или буква А, или часть изображения. Тип данных говорит как именно интерпретировать эти байты. В JavaScript типы: число, строка, булево значение, null, undefined, символ, объект. Первые шесть — примитивы. Объект — всё остальное.

**Что такое примитив и почему он копируется по значению.** Примитив — это простое неделимое значение. Число пять — это просто пять. Когда ты присваиваешь «let b равно a», и a это пять, b получает свою собственную копию числа пять. Изменение b не трогает a. Они живут отдельно.

**Что такое объект и почему он передаётся по ссылке.** Объект — это коллекция данных, которая живёт в куче — специальной области памяти для больших структур. Переменная хранит не сам объект, а адрес где он живёт. Когда ты делаешь «let b равно a», и a это объект, b получает тот же адрес. Обе переменные смотрят на один и тот же объект. Мутация через одну — видна через другую.

**Что такое область видимости.** Область видимости определяет где именно в коде доступна переменная. Переменная объявленная внутри фигурных скобок видна только внутри них — это блочная область видимости. Снаружи блока переменной не существует.

**Что такое прототип.** Каждый объект в JavaScript имеет скрытую ссылку на другой объект — свой прототип. Когда ты обращаешься к свойству и его нет в объекте, JavaScript идёт искать его в прототипе, потом в прототипе прототипа, и так далее до null. Это цепочка прототипов.

**Что такое функция первого класса.** В JavaScript функция — это такой же объект, как массив или словарь. Её можно присвоить переменной, передать как аргумент, вернуть из другой функции. Это не просто удобство — это основа асинхронного кода, замыканий и паттернов проектирования.

**Что такое модуль.** Модуль — это файл, который явно объявляет что он даёт другим файлам через export, и явно объявляет что берёт от других файлов через import. До модулей весь код жил в одном глобальном пространстве имён — переменные конфликтовали, зависимости были неочевидны.

**Что такое итерируемое.** Итерируемое — это любое значение, по которому можно пройтись в цикле. Массив итерируемый. Строка итерируемая. Объект — нет, если специально не сделать его итерируемым. Итерируемость — это контракт: у объекта должен быть метод Symbol.iterator который возвращает итератор.

**Что такое итератор.** Итератор — это объект с методом next. Каждый вызов next возвращает объект с двумя полями: value и done. Value — текущее значение. Done — булево, сигнализирует закончился ли поток. Итератор держит внутреннее состояние: знает где он находится в последовательности.

## СЛОЙ ПЕРВЫЙ. Принципы.

Это не объяснения — это правила. Короткие. Абсолютные. Если принцип нарушен в коде — где-то ошибка.

**Принцип первый.** var всплывает и имеет функциональную область видимости. let и const имеют блочную область видимости и не всплывают. В современном коде var не используется никогда. Без исключений.

**Принцип второй.** Примитивы передаются по значению. Объекты передаются по значению ссылки. Переназначить внешнюю переменную изнутри функции невозможно. Мутировать поля внешнего объекта — можно.

**Принцип третий.** ArrayBuffer — это сырая память без интерпретации. Uint8Array — это вид на неё как на массив байтов. Один буфер можно читать через разные представления одновременно. Web Crypto API работает с этими типами — без понимания разницы криптография будет тёмной магией.

**Принцип четвёртый.** ES6-модули статические: все импорты известны до выполнения. Это позволяет сборщику выбросить неиспользуемый код до загрузки в браузер. Динамический import — ленивый, возвращает Promise, выполняется в момент вызова.

**Принцип пятый.** Строгое сравнение через три знака равно не делает приведение типов. Нестрогое через два знака равно делает приведение — и результат часто удивляет. Для сравнения в продакшн-коде — только строгое.

**Принцип шестой.** WeakMap неитерируем не из-за ограничения, а по необходимости. Если бы его можно было итерировать, сборщик мусора не мог бы освободить ключи-объекты. Слабые ссылки и итерация несовместимы.

**Принцип седьмой.** Приватные поля с решёткой — это гарантия, а не конвенция. Подчёркивание перед именем — это просьба не трогать. Решётка — это синтаксическая ошибка при попытке доступа снаружи класса. Для хранилища приватного ключа нужна гарантия, а не просьба.

**Принцип восьмой.** Генератор вычисляет следующий элемент только при вызове next. Для бесконечного потока или очень большого набора данных — генератор, а не массив. Массив требует памяти для всех элементов сразу.

**Принцип девятый.** Поиск свойства идёт по цепочке прототипов вверх до null. Это не копирование свойств при наследовании — это делегирование поиска. Разница принципиальная: если прototип меняется после создания объекта — объект видит изменения.

**Принцип десятый.** Циклическая зависимость между модулями не ошибка компилятора — это тихий баг. Импортированное значение на верхнем уровне модуля при циклической зависимости будет undefined в момент инициализации.

## СЛОЙ ВТОРОЙ. Вопросы с принципами решения.

Здесь двадцать два вопроса. Услышав вопрос — останови запись. Попробуй ответить вслух. Потом продолжи — услышишь принцип который разблокирует ответ. Не решение — именно принцип.

---

**Вопрос первый.** Функция получила объект как аргумент и внутри переназначила параметр на пустой объект. Изменится ли переменная снаружи?

Принцип решения. Думай о том что именно передаётся в функцию. В функцию приходит копия ссылки — не сам объект и не ссылка на переменную, а копия адреса. Переназначение параметра меняет локальную копию адреса. Внешняя переменная по-прежнему держит старый адрес. Ответ: нет, не изменится. Но если бы внутри функции изменялись поля объекта — изменения были бы видны снаружи, потому что оба адреса ведут к одному объекту в куче.

---

**Вопрос второй.** Что вернёт оператор typeof применённый к null и почему это нельзя исправить?

Принцип решения. Думай об обратной совместимости как о техническом долге. typeof null возвращает строку object — это баг первой реализации JavaScript где null хранился как нулевой тег типа объекта. Исправить нельзя: весь существующий код который проверяет typeof на object сломается. Это классический пример как решение принятое в 1995 году за десять дней консервируется в спецификации навсегда. Для проверки на null используй только строгое сравнение с null.

---

**Вопрос третий.** В чём разница между var, let и const с точки зрения области видимости и всплытия?

Принцип решения. Думай о трёх характеристиках: где живёт переменная, когда она доступна, можно ли переназначить. var живёт в функции или в глобальной области, всплывает в начало функции и доступна до объявления со значением undefined, переназначать можно. let живёт в блоке, не всплывает — обращение до объявления вызывает ошибку, переназначать можно. const живёт в блоке, не всплывает, переназначить нельзя — но мутировать поля объекта можно. const не делает объект неизменяемым, он делает переменную непереназначаемой.

---

**Вопрос четвёртый.** Когда Map лучше Object, а когда Object лучше Map?

Принцип решения. Думай о трёх сценариях. Map лучше когда ключи не строки — числа, объекты, символы. Map лучше когда нужен гарантированный порядок вставки. Map лучше когда часто проверяешь размер — у Map есть свойство size, у Object нужно каждый раз создавать массив ключей. Object лучше когда ключи — строки или идентификаторы и нужен быстрый доступ, когда нужна сериализация в JSON, когда работаешь с прototypeными методами. В Event Store идентификатор события — строка, но нужна O(1) проверка наличия и гарантированный размер — там Map.

---

**Вопрос пятый.** Зачем ArrayBuffer существует отдельно от Uint8Array? Разве это не одно и то же?

Принцип решения. Думай об отделении хранилища от интерпретации. ArrayBuffer — это N байтов памяти без смысла, просто сырые данные. Uint8Array — это вид на эту память как на массив восьмибитных чисел без знака. Один и тот же буфер можно читать через Uint32Array как числа и через Uint8Array как байты одновременно. Криптографические функции возвращают ArrayBuffer. Чтобы увидеть его содержимое — нужно создать вид. Без понимания этого разделения работа с Web Crypto превращается в угадывание.

---

**Вопрос шестой.** В чём разница Set и массива с уникальными значениями? Зачем Event Store использует Set?

Принцип решения. Думай о сложности проверки принадлежности. Метод includes у массива работает за время пропорциональное размеру — нужно пройти все элементы. Метод has у Set работает за постоянное время независимо от размера — это хеш. При десяти тысячах событий в хранилище и потоке в сто событий в секунду разница между O(N) и O(1) — это разница между перегруженным и незагруженным процессором.

---

**Вопрос седьмой.** Почему WeakMap не итерируется — это ограничение или необходимость?

Принцип решения. Думай о том что знает сборщик мусора. Сборщик освобождает память от объектов на которые больше нет ссылок. Если бы WeakMap был итерируемым, сборщик не мог бы знать будет ли ещё итерация — вдруг кто-то позже пройдётся по ключам. Значит нельзя освобождать ни один ключ. Но тогда это не слабые ссылки — это обычные. Неитерируемость — не ограничение реализации, это единственный способ сделать ссылки действительно слабыми.

---

**Вопрос восьмой.** Чем итерируемый отличается от итератора?

Принцип решения. Думай о разделении ответственности. Итерируемый знает как создать итератор — у него есть метод Symbol.iterator. Итератор знает как перейти к следующему элементу — у него есть метод next, который возвращает объект со значением и флагом завершения. Строка — итерируемая. Результат вызова строкового Symbol.iterator — итератор. Цикл for of сначала вызывает Symbol.iterator, потом многократно next. Передать итератор туда где ожидается итерируемое — тихий баг, не ошибка.

---

**Вопрос девятый.** Зачем генератор для потока событий если можно вернуть массив?

Принцип решения. Думай о ленивости и о прерывании. Массив из десяти тысяч событий — все в памяти сразу, сразу. Генератор вычисляет следующий элемент только когда его просят — один элемент в памяти в каждый момент. Но важнее другое: генератор позволяет корректно останавливаться. Цикл for of с break вызовет метод return на генераторе — cleanup произойдёт. С массивом нельзя частично прочитать без создания промежуточной копии. Для курсора IndexedDB, WebSocket-потока, пагинации — генератор естественнее.

---

**Вопрос десятый.** В чём разница между фабричной функцией и конструктором с new?

Принцип решения. Думай о контроле над созданием объекта. Фабрика — обычная функция. Может вернуть разные типы в зависимости от аргументов. Может отказать с понятным сообщением ещё до создания объекта. Не привязана к new — забыть её вызвать невозможно. Конструктор с new всегда возвращает экземпляр. Если забыть new в нестрогом режиме — this становится глобальным объектом, баг тихий и коварный. Для доменных объектов где создание должно проходить валидацию — фабрика даёт больше контроля.

---

**Вопрос одиннадцатый.** Почему приватные поля с решёткой лучше конвенции с подчёркиванием для хранилища ключей?

Принцип решения. Думай о разнице между просьбой и гарантией. Подчёркивание — это договорённость: пожалуйста, не читай это поле. Но ничто технически не мешает написать имя поля с подчёркиванием напрямую и прочитать значение. Решётка — это синтаксическое ограничение движка: попытка прочитать поле снаружи класса вызовет ошибку ещё до выполнения. Для хранилища в котором лежит secp256k1 приватный ключ это не вопрос стиля — это вопрос безопасности.

---

**Вопрос двенадцатый.** Что такое цепочка прототипов и как JavaScript ищет свойство?

Принцип решения. Думай о делегировании, а не о копировании. При обращении к свойству JavaScript сначала ищет его в самом объекте. Если не нашёл — идёт в прototип. Не нашёл — идёт в прototип прototипа. И так до null. Это не значит что свойства копируются при создании наследника. Это значит что поиск делегируется вверх по цепочке. Если прototип изменить после создания объекта — объект увидит изменение. В этом и красота и опасность.

---

**Вопрос тринадцатый.** Почему ES6-модули статические и что это даёт на практике?

Принцип решения. Думай о том что сборщик знает до запуска. Все импорты и экспорты известны в момент разбора файла — ещё до выполнения кода. Сборщик может построить полное дерево зависимостей и выбросить всё что не используется. Это tree-shaking. Динамический import через функцию — ленивый, выполняется в момент вызова, возвращает Promise. Его нельзя убрать при сборке. Статические импорты в начале файла — для core зависимостей. Динамические — для ленивой загрузки крупных модулей по требованию.

---

**Вопрос четырнадцатый.** Что такое циклическая зависимость и когда она становится проблемой?

Принцип решения. Думай о порядке инициализации. Модуль А импортирует из модуля Б. Модуль Б импортирует из модуля А. При загрузке А движок начинает его инициализацию, встречает импорт Б, инициализирует Б. Б хочет что-то из А, но А ещё не инициализирован — получает undefined. Это тихий баг, не ошибка. Опасно только когда импортированное значение используется на верхнем уровне модуля при инициализации. Если импорты используются внутри функций — к моменту вызова оба модуля уже готовы. Лечение: вынести общую зависимость в третий модуль.

---

**Вопрос пятнадцатый.** Зачем в Set есть метод has если можно сделать Array и использовать includes?

Принцип решения. Этот вопрос уже был под другим углом, но здесь важна другая грань. Думай о семантике а не только о скорости. includes говорит компьютеру: пройди все элементы и проверь каждый. has говорит: у тебя есть хеш, проверь по нему. Даже если скорость была бы одинаковой — Set выражает намерение: это коллекция уникальных элементов, порядок не важен, мне важно только наличие или отсутствие. Код который выражает намерение читается и поддерживается лучше.

---

**Вопрос шестнадцатый.** Что делает Object.defineProperty и зачем это нужно?

Принцип решения. Думай о метаданных свойства. Обычное присваивание создаёт свойство с настройками по умолчанию: перечислимое, изменяемое, удаляемое. Object.defineProperty позволяет задать точные характеристики: enumerable определяет виден ли ключ в for-in и Object.keys, writable определяет можно ли изменить значение, configurable определяет можно ли изменить сами характеристики или удалить свойство. Для создания объекта с защищёнными полями — например константами конфигурации которые нельзя случайно перезаписать — это правильный инструмент.

---

**Вопрос семнадцатый.** Как работает сборка мусора методом меток и в чём его преимущество перед подсчётом ссылок?

Принцип решения. Думай о достижимости из корня. Метод меток начинает с корневых объектов — глобальный объект, стек вызовов — и помечает всё что достижимо через ссылки. Всё непомеченное — мусор. Подсчёт ссылок считает сколько переменных ссылается на объект. Когда счётчик падает до нуля — объект удаляется. Проблема подсчёта ссылок: циклические ссылки. А ссылается на Б, Б ссылается на А — счётчики никогда не падают до нуля, память утекает. Метод меток циклические ссылки обрабатывает корректно — если цикл недостижим из корня, он помечается как мусор.

---

**Вопрос восемнадцатый.** Почему нельзя прервать forEach через return?

Принцип решения. Думай о том кто вызывает колбэк. forEach вызывает переданную функцию для каждого элемента. Когда ты пишешь return внутри этой функции, ты возвращаешь значение из колбэка — в forEach. forEach игнорирует возвращённое значение и продолжает итерацию. Ты не можешь из колбэка управлять внешним циклом. Для прерывания нужен for of с break, или метод find если ищешь первый элемент, или метод some если проверяешь условие.

---

**Вопрос девятнадцатый.** Что такое деструктурирование и чем оно отличается от простого присваивания?

Принцип решения. Думай об извлечении по структуре. Деструктурирование позволяет извлекать несколько значений из объекта или массива за одну операцию, опираясь на структуру, а не на последовательные обращения. Из объекта извлекаешь по именам ключей. Из массива — по позиции. Можно задать новые имена при извлечении. Можно задать значения по умолчанию. Можно вложить — деструктурировать вложенные объекты. В параметрах функции деструктурирование делает API функции самодокументируемым: сразу видно какие поля объекта функция использует.

---

**Вопрос двадцатый.** Чем CommonJS отличается от ES6-модулей принципиально?

Принцип решения. Думай о статическом против динамического. CommonJS — это require в момент выполнения. Путь к модулю может быть вычислен во время работы программы. Всё что экспортируется — это один объект который можно модифицировать после экспорта. ES6-модули — статические. Путь к модулю известен до выполнения. Экспортируются живые привязки: если экспортируемое значение изменится в модуле-источнике — импортёр увидит новое значение. Смешивать их в одном файле нельзя. В браузере работают только ES6-модули.

---

**Вопрос двадцать первый.** Что такое Symbol и зачем он нужен?

Принцип решения. Думай о гарантированной уникальности. Symbol — это примитивное значение, которое всегда уникально. Каждый вызов Symbol создаёт новое уникальное значение — даже если передать одинаковую строку-описание. Это позволяет создавать ключи свойств которые не конфликтуют ни с чем. Symbol.iterator — это встроенный символ который используется протоколом итерации. Если ты добавляешь свойство с ключом-символом к чужому объекту — ты не рискуешь затереть что-то существующее.

---

**Вопрос двадцать второй.** Почему const не делает объект неизменяемым?

Принцип решения. Думай о том что именно const защищает. const запрещает переназначение переменной — ты не можешь сделать так чтобы переменная указывала на другой объект. Но содержимое объекта — его поля — можно изменять. const защищает связь переменной с объектом, а не объект изнутри. Для настоящей неизменяемости нужен Object.freeze — он запрещает добавление, удаление и изменение свойств. Но freeze поверхностный: вложенные объекты замораживаются только если заморозить их отдельно.

---

## СЛОЙ ТРЕТИЙ. Красные флаги.

Это список ошибок. Слушай медленно. Если что-то кольнуло — значит вчера это было сделано неправильно.

Первый флаг. Использую var — всплытие и функциональная область видимости создают баги которые трудно найти. Только let и const.

Второй флаг. Сравниваю объекты через строгое равенство ожидая сравнения содержимого. Это сравнение ссылок. Два разных объекта с одинаковым содержимым — не равны через строгое равенство.

Третий флаг. Пробую прервать forEach через return. Он не прерывается. Для прерывания — for of с break.

Четвёртый флаг. Мутирую объект-аргумент внутри функции без намерения изменить внешнее состояние. Side effect без намерения — источник трудноуловимых багов.

Пятый флаг. Передаю итератор туда где ожидается итерируемое. Это не ошибка, это тихий баг — поведение непредсказуемо.

Шестой флаг. Храню критичные данные в поле с подчёркиванием вместо поля с решёткой. Подчёркивание — это просьба. Решётка — гарантия.

Седьмой флаг. Пишу new String с большой буквы или new Number с большой буквы. Это создаёт объект-обёртку, а не примитив. typeof вернёт object. Почти всегда это ошибка.

Восьмой флаг. Использую Array для частых проверок принадлежности на больших данных. includes на массиве — это линейный поиск. Нужен Set.

Девятый флаг. Создаю WeakMap с примитивным ключом — числом или строкой. Это TypeError. Ключи WeakMap только объекты и символы.

Десятый флаг. Смешиваю require и import в одном файле. В браузере это синтаксическая ошибка.

Одиннадцатый флаг. Использую импортированное значение на верхнем уровне модуля в ситуации с циклической зависимостью. В момент инициализации это значение будет undefined.

Двенадцатый флаг. Забываю что const не замораживает объект. Поля объекта объявленного через const можно изменять.

Тринадцатый флаг. Полагаюсь на конвенцию подчёркивания для приватности вместо использования синтаксической защиты. Договорённости нарушаются. Синтаксис — нет.

## СЛОЙ ЧЕТВЁРТЫЙ. Метафоры.

Здесь технические принципы переведены в жизненный опыт. Не для запоминания правил — для понимания их природы.

---

**Метафора первая. var против let и const — три типа договорённостей.**

var похож на слух. Ты сказал что-то в одной комнате — слух разошёлся по всему этажу. Никто не просил его распространяться, но он всплыл туда где его не звали. let похож на разговор за закрытой дверью — слышно только внутри этой комнаты, снаружи ничего. const похож на татуировку на запястье — связь с ценностью записана, переназначить нельзя. Но ценности внутри — убеждения, отношение, поведение — могут меняться.

Урок для отношений. Есть люди с которыми у тебя var-договорённость: всё что ты скажешь расползётся за пределы разговора. Есть let-люди: то что сказано между вами, остаётся между вами. Есть const-люди: связь не переназначается, но отношения внутри evolve. Выбирай тип договорённости осознанно, а не по умолчанию.

---

**Метафора вторая. Передача по ссылке — ты даёшь ключ, а не копию.**

Когда ты передаёшь объект в функцию — это как дать кому-то ключ от квартиры. Они могут зайти, переставить мебель, изменить всё внутри. Но они не могут взять и отдать твою квартиру другим людям — ключ у них, квартира твоя. Переназначить нельзя, мутировать можно.

Урок для карьеры. Когда ты делегируешь задачу — ты даёшь ключ. Человек может изменить как она выглядит внутри. Но исчезнуть с задачей — забрать твою квартиру — он не может если ответственность осталась у тебя. Делегирование — это ключ, не передача права собственности.

---

**Метафора третья. Сборка мусора — отпускай то что больше недостижимо.**

Сборщик мусора начинает с того что знает точно — корни, которые живут. Всё что достижимо из живого — живо. Всё остальное — мусор, который можно освободить. Он не считает сколько раз на что-то смотрели. Он спрашивает: есть ли живой путь к этому объекту от чего-то важного?

Урок для жизни. Есть отношения, проекты, привычки которые занимают место в голове но недостижимы из твоих настоящих ценностей — нет живого пути от того что тебе важно к ним. Это психологический мусор. Его не нужно насильно выбрасывать — он сам собирается когда перестаёшь искусственно держать ссылки.

---

**Метафора четвёртая. WeakMap — хорошее расставание.**

WeakMap хранит данные привязанные к объектам-ключам. Если объект исчезает — данные исчезают вместе с ним. Нет удержания. Нет накопления. Если ключа больше нет в жизни системы — связанное с ним автоматически уходит.

Урок для отношений. Хорошее расставание работает как WeakMap. Воспоминания, привязки, ожидания связанные с человеком — они освобождаются когда человек уходит из жизни, а не копятся годами. Удерживать связанные данные после исчезновения ключа — это утечка памяти. И психологической, и буквальной.

---

**Метафора пятая. ArrayBuffer и Uint8Array — одни данные, разный смысл.**

Одни и те же байты можно читать как числа, как текст, как пиксели изображения. Данные не несут смысл сами по себе — смысл возникает через интерпретацию.

Урок для общения. Одно и то же действие человека — опоздал на встречу — можно прочитать как неуважение, как рассеянность, как загруженность, как тревожное расстройство. Данные одни. Интерпретация разная. Прежде чем реагировать — уточни через какой вид ты смотришь. Может стоит попробовать другой.

---

**Метафора шестая. Область видимости — что происходит в Лас-Вегасе, остаётся в Лас-Вегасе.**

Переменная внутри блока видна только внутри. Снаружи её не существует. Это не секретность — это организация. Хорошо спроектированный код держит переменные в минимально необходимой области. Меньше область — меньше мест где что-то может пойти не так.

Урок для дома и порядка. Каждая вещь должна жить в минимально необходимом контексте. Ножи в кухне. Документы в папке. Зарядка у рабочего стола. Когда вещь выходит за пределы своей области — теряется и создаёт шум. Порядок — это правильная область видимости для вещей.

---

**Метафора седьмая. Статические импорты — знай зависимости до старта.**

ES6-модули требуют объявить все зависимости в начале файла до выполнения любого кода. Ты не можешь начать работу и по ходу обнаружить что тебе нужно что-то критическое.

Урок для карьеры. Прежде чем начать проект — составь полный список зависимостей. Что тебе нужно: инструменты, люди, разрешения, бюджет, информация. Обнаружить критическую зависимость в середине — это как динамический import в критическом пути. Всё замирает и ждёт.

---

**Метафора восьмая. Циклическая зависимость — созависимые отношения.**

А зависит от Б, Б зависит от А. Ни один не может функционировать без другого и ни один не может быть инициализирован первым. Система зависает.

Урок для отношений. Созависимость — это циклическая зависимость между людьми. А не может принять решение без одобрения Б. Б не чувствует себя нужным без А в роли зависимого. Решение в программировании: вынести общую зависимость в третий независимый модуль. Решение в жизни: найти независимый фундамент — ценности, интересы, идентичность — который принадлежит каждому отдельно.

---

**Метафора девятая. Строгое сравнение — сравнивай то что реально сравниваешь.**

Нестрогое сравнение делает скрытые преобразования. Ноль равен пустой строке. Null равен undefined. Истина встроена в числа. Ты думаешь что сравниваешь одно — на самом деле что-то другое.

Урок для принятия решений и покупок. Сравнивая два варианта убедись что сравниваешь одно и то же. Смартфон за двадцать тысяч сейчас против смартфона за тридцать через полгода — если не привести к одному временному контексту, сравнение нестрогое. Новая работа с большей зарплатой но дальше — надо привести к одной метрике. Нестрогое сравнение создаёт решения о которых потом сожалеешь.

---

**Метафора десятая. Генератор — не планируй всё наперёд.**

Генератор не вычисляет весь результат заранее. Он отдаёт следующее значение только когда его просят. Это ленивость как архитектурный принцип.

Урок для карьеры и жизни. Не нужно иметь план на десять лет вперёд. Следующий шаг становится виден только после того как сделан текущий. Попытка спланировать всё до конца — это загрузить в память массив всей жизни. Это невозможно и это замораживает. Генераторная жизнь: сделай следующий шаг, получи следующее значение, сделай следующий шаг.

---

**Метафора одиннадцатая. Приватные поля с гарантией — граница с защитой, а не с просьбой.**

Подчёркивание перед именем — это просьба не трогать. Решётка — это гарантия: невозможно физически. Одно и то же намерение реализованное по-разному имеет принципиально разный результат.

Урок для личных границ. Граница о которой ты просишь — это подчёркивание. Граница которую ты защищаешь действием — это решётка. Вежливая просьба не делать что-то снова и снова нарушаемое — это конвенция которую никто не соблюдает. Последствие которое действительно наступает — это синтаксическая защита. Реальная граница — это та у которой есть enforcement.

---

**Метафора двенадцатая. typeof null — технический долг как репутационный багаж.**

Баг принятый в 1995 году нельзя исправить в 2025 году потому что весь существующий код завязан на это поведение. Это цена обратной совместимости.

Урок для карьеры. Решения принятые быстро в начале карьеры становятся частью твоей репутации. Некоторые нельзя просто взять и исправить — слишком много людей уже завязано на это поведение. Можно только работать вокруг. Именно поэтому ранние решения — с кем работаешь, как общаешься, что подписываешь — стоит принимать осторожно.
