## Что должно быть в голове в конце этапа

1. Замыкание как механизм памяти функции, в том числе для **мемоизации** (синергия с Венгроу гл. 12).
2. `this` в шести контекстах: прямой вызов, метод, конструктор, стрелка, явный bind/call/apply, в классе. Без раздумий.
3. Currying и partial application — когда применять, не путать.
4. Рекурсия в JS: глубина стека по умолчанию (~10к в V8), почему хвостовая рекурсия не оптимизируется (нет TCO в большинстве браузеров).
5. Promise lifecycle: pending → fulfilled / rejected. Микротаска vs макротаска.
6. async/await: семантически идентичен `.then()`, но не идентичен по обработке ошибок — try/catch охватывает только то, что внутри await.
7. Promise.all (fail-fast) vs Promise.allSettled (без fail-fast) vs Promise.any (первый успех) vs Promise.race (первый любой). Точное знание, какой когда.
8. Гонки и race conditions в async коде (например, два одновременных вызова `loadProfile()` могут перезаписать друг друга в state).
9. Web Crypto API: `crypto.subtle.*` — асинхронен, работает на `ArrayBuffer`/`Uint8Array`, никогда на строках напрямую.
10. **Различие** между `crypto.getRandomValues()` (синхронно, для нонсов) и `crypto.subtle.*` (асинхронно, для всего сложного).
11. Классы с приватными полями (`#`) и accessors (`get`/`set`) — когда стоит и когда нет.

## Заметки по риску

- **Proxy ловушки на `has` и `deleteProperty`.** Самые частые баги. Если trap не вернул boolean — TypeError на ровном месте. Покрывать тестами явно.
- **Web Crypto API не делает то, что вы ожидаете (этап 2 это уже показал).** На этой этапе главная ловушка — забыть, что `nonce` обязан быть уникальным на каждое шифрование. Иначе AES-GCM компрометирован. Реализовать через `crypto.getRandomValues(new Uint8Array(12))` каждый раз, явный комментарий в коде.
- **Тест-векторы шифрования БД.** Их нет в спеке (это локальное шифрование, не межклиентское). Тесты должны быть round-trip + проверка отказа при подделке тега.
- **Соблазн использовать Dexie hooks вместо Proxy.** Hooks проще, но они не покрывают `where(...).equals(...)` чтения и не дают единой точки для ошибок. Эссе из обязательных артефактов закрывает решение явно.
- **Глотание ошибок в крипто-коде.** Никогда. Если `decryptRow` бросил — это либо испорченный `dbKey`, либо тампер БД. Оба случая — критичные, должны логироваться и пробрасываться вверх до UI с разблокировкой через `unlock.jsx`.

## Заметки по риску (JS)

- **WebSocket в Node для тестов.** Браузерный API не работает в Node-тестах напрямую. Использовать `ws` пакет или mock. Это легко — 5 строк, но вспомнить нужно.
- **Comlink не передаёт ошибки прозрачно по умолчанию.** Сериализация Error через postMessage теряет stack. Использовать `comlink/extras` или явно сериализовать ошибки.
- **AUTH event с созревшим created_at.** Если у клиента часы убежали — relay отвергнет AUTH. F-RL-06 это предупреждает; реализуйте предупреждение в UI **до** попытки AUTH, не после третьего отказа.
- **Reconnect storm.** Если один сервер падает — все клиенты пытаются reconnect одновременно. Jitter 20% — минимум; в продакшене берут 30–50%.
- **NIP-01 строгий парсинг.** Не использовать `eval`, не доверять формату. JSON.parse + проверка структуры до использования полей.
- **Подпись событий до отправки.** Никогда не подписывать в main thread, если на это уходит > 50 мс. UI заблокируется.

- Canvas 2D: контекст рисования, базовые операции (rect, arc, fillText). **Только обзор** — глубина не нужна для DM-чата.
- Когда CSS, когда WAAPI, когда canvas. Для message-bubble fade-in, scroll-into-view — CSS. Для voice waveform (этап 7) — canvas.

**Формы (Frisby 18):**

- HTML form-элементы и их свойства из JS: `<input>`, `<textarea>`, `<select>`, `<button>`.
- Свойства `value`, `checked`, `selectedIndex`. Чем `value` отличается от `defaultValue`.
- События формы: `input`, `change`, `submit`, `focus`, `blur`. Когда какое.
- `FormData` API — стандартный сериализатор формы.
- Валидация: HTML5 (`required`, `pattern`, `minLength`/`maxLength`) vs custom через JS.
- `<textarea>` особенности: авто-resize, Enter vs Shift+Enter (отправка vs новая строка).

**API в JavaScript (Frisby 19, частично):**

- IntersectionObserver — наблюдатель за пересечением элементов с viewport. **Прямое применение в lazy-chat** (триггер подгрузки старых сообщений при скролле вверх).
- Page Visibility API: `document.visibilityState`, событие `visibilitychange`. Чтобы не показывать desktop-уведомление, когда вкладка активна.
- Notification API: `Notification.requestPermission()`, `new Notification(title, options)`. Ограничения (только в Secure Context, требуется user gesture).
- Clipboard API — для «скопировать pubkey контакта».
- ResizeObserver — обзор без углубления.

## Контрольные точки приёмки этапа (само-экзамен)

1. Анимировать `<div>` от opacity 0 до 1 за 300 мс — тремя способами (CSS transition, CSS keyframes, WAAPI). Сравнить, какой проще для одноразового события.
2. Реализовать textarea с авто-resize: высота элемента подстраивается под контент, до максимума 200 px, потом — скролл.
3. Реализовать счётчик символов с предупреждением при > 80% от 10000 символов и блокировкой кнопки отправки при > 10000.
4. Реализовать lazy-load: при скролле к верхней границе списка — подгружаются ещё 100 элементов, sentinel пересоздаётся.
5. Реализовать desktop-уведомление о новом DM: только если `document.visibilityState === 'hidden'` и пользователь дал permission.
6. Объяснить, почему `setInterval(() => render(), 16)` — плохая замена `requestAnimationFrame`. (Hint: tab inactive, дрейф, vsync.)

## Связь с другими треками

- **Венгроу 16 (priority queue) ↔ outbox UI:** UI должен показывать «отправляется», «не отправлено — повторить через X сек», что соответствует state машины сообщения. Обновления приходят из outbox через сигналы.
- **Frisby 16 (события — этап 5) ↔ Frisby 18 (формы):** обработчики формы — это `addEventListener('input', ...)` под капотом, но с особенностями реактивных свойств (`value` биндится).
- **Frisby 19 (IntersectionObserver) ↔ § 12.3 lazy-load:** прямое применение. Без IntersectionObserver lazy-load писался бы через `scroll`-event с throttle, а это — anti-pattern.
- **Frisby 19 (Notification) ↔ § 12.3 + AC-IB-01:** уведомление о DM от не-contact pubkey — отдельный UX-сценарий.

## Особенности этапа

**Glow до сих пор был на DOM/событиях; теперь — на API и формах.** Это где-то 60% повседневной фронтенд-работы — формы, валидация, обработка ввода. Не недооценивать `<textarea>` — он коварнее, чем кажется (особенно с авто-resize и Enter-семантикой).

**`document.execCommand('copy')` — не использовать.** Устарел. Только `navigator.clipboard.writeText`. На небезопасном контексте (HTTP) — недоступен; для Ugolok это не проблема (NF-06: Web Crypto требует HTTPS, значит, и Clipboard работает).

**IntersectionObserver — единственный современный способ lazy-load.** Если в коде проекта замечено `addEventListener('scroll', ...)` для подгрузки — это технический долг. Зафиксировано в Anki.

**Notification API.** На iOS Safari — частично работает. На macOS Safari — работает с пользовательским разрешением. Не строить критическую функциональность на уведомлениях; это украшение, а не основа UX. Основа — `unread counter` в UI, который есть и без notifications.

# Этап 8 — JavaScript (Frisby)

**Связка с фазой ТЗ:** § 13.9 — финальная сборка (AC-11 размер бандла, AC-15 self-host docs); финальный аудит производительности и качества кода.
**Главы Frisby:** **25 (Модули)**, **27 (Лучшие практики)**, **20 (Отладка)**.
**Подход:** все три главы — реальная финализация Ugolok-сборки. Это не теория ради теории: tree-shaking → AC-11, debugging — для прохождения AC-12/13, best practices — для коммита кода в открытый репозиторий с прицелом на портфолио.

**Что должно быть в голове в конце этапа:**

- ESM vs CommonJS: семантика, статическая природа ESM, почему динамический `require` ломает tree-shaking. `import.meta.url`, top-level `await`.
- Dynamic import (`import()`) — Promise-based, code splitting, route-based загрузка. Разница с `import` верхнего уровня.
- Tree-shaking: bundler выкидывает unused exports. Side-effect-аннотация `"sideEffects": false` в `package.json`. Почему `import _ from 'lodash'` ломает tree-shaking, а `import debounce from 'lodash/debounce'` — нет.
- Vite-конкретное: rollup под капотом, `build.rollupOptions`, manualChunks, vite-plugin-singlefile (используется в Ugolok для производства одного `index.html`).
- Профайлинг JS: Performance tab DevTools, flame chart, sources tab с CPU profiling. Memory tab — heap snapshot, retainers, поиск утечек.
- Source maps в production: external vs inline. Trade-off: inline увеличивает bundle; external — два файла. Для Ugolok с vite-plugin-singlefile → `build.sourcemap: 'hidden'` или `false`.
- Best practices security: CSP, SRI, отсутствие `eval`, безопасное использование `innerHTML`, защита от XSS в Preact/React (default экранирование).
