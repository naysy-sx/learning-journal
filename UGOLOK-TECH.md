## 1. Назначение и область применения

### 1.1. Назначение

Ugolok — веб-приложение для приватной коммуникации и публикации контента. Приложение реализует защищённый обмен сообщениями, ведение блогов с гранулярным контролем доступа и управление контактами. Все данные хранятся локально на устройстве пользователя и синхронизируются между устройствами через сеть Nostr relay — промежуточных серверов, не имеющих доступа к содержимому.

### 1.2. Ключевые свойства

- **Децентрализация.** Нет центрального сервера. Relay взаимозаменяемы.
- **Приватность.** Содержимое зашифровано. Relay видит только минимально необходимые метаданные.
- **Мультиустройство.** Пользователь входит в свой аккаунт с любого устройства по мнемонике и видит единую среду: контакты, чаты, блоги, настройки.
- **Автономность.** Приложение работает офлайн. Синхронизация происходит при появлении сети.

### 1.3. Целевая платформа

Единственный HTML-файл, работающий в современном браузере (Chrome 90+, Firefox 90+, Safari 15+) без серверной части. Приложение функционирует офлайн после первой загрузки.

## 3. Архитектура системы

### 3.1. Архитектурный принцип

Приложение построено на принципе **Event Sourcing**: состояние не хранится напрямую, а вычисляется из упорядоченной последовательности неизменяемых подписанных событий.

Формально:

$$State_{t} = fold(State_0,\; [e_1, e_2, \ldots, e_t])$$

где $e_i$ — подписанное событие, $fold$ — детерминированная чистая функция.

**Обоснование выбора.** Требования к системе: (а) данные подписаны автором, (б) воспроизводимы на любом устройстве, (в) синхронизируемы без центрального арбитра, (г) доступны с любого устройства при наличии ключа. Эта модель совпадает с моделью событий протокола Nostr, что устраняет несоответствие между внутренней и транспортной моделями.

**Следствие для мультиустройства.** Поскольку состояние — функция от событий, а события хранятся на relay, любое устройство с приватным ключом может скачать события и вычислить идентичное состояние.

### 3.2. Гибридная модель событий

Протокол Nostr различает два класса событий с принципиально разной семантикой хранения на relay. Архитектура использует оба класса по назначению:

| Класс              | Kind-диапазон | Поведение relay                                             | Семантика fold             | Примеры                  |
| ------------------ | ------------- | ----------------------------------------------------------- | -------------------------- | ------------------------ |
| **Журнальные**     | 1000–9999     | Хранит **все** события                                      | Упорядочить, применить все | Сообщения (kind 1059)    |
| **State-snapshot** | 30000–39999   | Хранит только **последнее** на каждый (pubkey, kind, d-tag) | Взять последнее по d-tag   | Группы, права, настройки |

**Следствие для fold:**

- Для журнальных событий: `fold([e1, e2, ..., en])` — полная реконструкция истории.
- Для state-snapshot событий: `fold([e_latest])` — применение единственного актуального события; история изменений локальна и не воспроизводится с relay.

**Следствие для холодного старта:**

- Журнальные события: скачивается **полная история** с relay → воспроизводится точно.
- State-snapshot события: скачивается **текущее состояние** с relay → история изменений недоступна (принято и задокументировано как ограничение).

### 3.3. Модель данных

| Категория данных                                        | Где хранится                                    | Восстановимо с relay?      | Пояснение                                          |
| ------------------------------------------------------- | ----------------------------------------------- | -------------------------- | -------------------------------------------------- |
| Приватный ключ                                          | Только локально (IndexedDB, зашифрован паролем) | **Нет**                    | Переносится через мнемонику (12 слов)              |
| Публичные события (профиль kind 0, контакт-лист kind 3) | Локально + relay                                | **Да**                     | Replaceable: скачивается последний snapshot        |
| State-snapshot события (группы, права, настройки)       | Локально + relay                                | **Да** (текущее состояние) | Parameterized replaceable: только latest per d-tag |
| Сообщения (kind 1059, Gift Wrap)                        | Локально + relay                                | **Да** (полная история)    | Журнальные события, relay хранит все               |
| Materialized views (кэш прав, деревья)                  | Только локально                                 | **Вычисляются**            | Пересчитываются из событий при холодном старте     |

**Вывод:** единственное, что невосстановимо — приватный ключ (32 байта). История изменений state-snapshot объектов также не воспроизводима с relay, но текущее состояние — да.

## 4. Математические основания

### 4.1. Данные и сущности

**Функциональность:** пользователи, контакты, группы контактов, ресурсы (блоги, посты, чаты), иерархия ресурсов.

**Математическая модель:** конечные множества, бинарные отношения, частично упорядоченные множества (деревья).

**Почему эта модель.** Пользователи и ресурсы — конечные перечислимые наборы объектов. Связи между ними (контакт, членство, владение) — подмножества декартова произведения, то есть бинарные отношения. Иерархия «блог → пост → комментарий» образует дерево — частный случай частичного порядка с единственным путём к корню.

**Структуры данных и алгоритмы:**

| Объект                                      | Структура                                | Обоснование                                                                                                    |
| ------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Множество с проверкой $\in$                 | Hash Set / Bitset                        | $O(1)$ проверка. Bitset при плотной нумерации: $\cup = $ OR, $\cap = $ AND, $\setminus = $ AND NOT за $O(n/w)$ |
| Бинарное отношение $R \subseteq A \times B$ | Hash Map: $a \to$ Set$\langle b \rangle$ | Образ элемента за $O(1)$. Эффективное представление разреженной матрицы смежности                              |
| Дерево (иерархия)                           | Parent-указатель + DFS Euler Tour        | Проверка «$v$ потомок $u$» за $O(1)$: $in_u \leq in_v \leq out_u$                                              |

### 4.2. Авторизация и права доступа

**Функциональность:** определение прав пользователей и групп к ресурсам, комбинирование прав, разрешение конфликтов (allow/deny), кэширование.

**Математическая модель:** решётка подмножеств, трёхзначная логика.

**Почему решётка.** Множество действий $A = \{view, comment, chat, write, moderate, admin\}$. Набор разрешённых действий — элемент $2^A$. Множество $2^A$ с $\cup$ и $\cap$ — булева алгебра (частный случай решётки). Изоморфизм $2^A \cong \{0,1\}^{|A|}$ позволяет реализовать все операции через побитовую арифметику: $\lor = $ OR, $\land = $ AND. Это не аналогия — математический изоморфизм.

**Почему трёхзначная логика.** Каждое правило: allow, deny или undefined. Правило «deny побеждает» реализуется как: $effective = allow \;\&\; {\sim}deny$. Кодирование: два бита на действие (allow_mask, deny_mask). Семантика **fail-closed**: undefined (ни allow, ни deny) → $0 \;\&\; \sim 0 = 0$ → denied по умолчанию. Это корректное поведение для системы безопасности.

**Структуры данных и алгоритмы:**

| Объект               | Структура                             | Алгоритм                                         |
| -------------------- | ------------------------------------- | ------------------------------------------------ |
| Решётка $2^A$        | Битовая маска (int)                   | Join = OR, Meet = AND, $O(1)$                    |
| Трёхзначная логика   | Пара int (allow_mask, deny_mask)      | $effective = allow \;\&\; {\sim}deny$, $O(1)$    |
| Кэш эффективных прав | Hash Map: $(user, resource) \to mask$ | Lookup $O(1)$, инвалидация по графу зависимостей |

**Алгоритм инвалидации кэша (MVP-вариант — полный пересчёт):**

```
on event(kind in {3, 30050, 30051}):
  effectivePerms.clear()   // для затронутого owner
  rebuildCache(owner):
    for each (subject, resource) in permissions(owner):
      mask ← computeEffective(subject, resource)
      effectivePerms.set([owner+subject+resource], mask)
```

При $|permissions| \leq 10^4$ полный пересчёт занимает <100мс — приемлемо. Гранулярная инвалидация по графу зависимостей вынесена в backlog.

### 4.3. Состояния объектов

**Функциональность:** жизненный цикл сообщения, поста, соединения с relay.

**Математическая модель:** детерминированный конечный автомат $(S, \Sigma, \delta, s_0, F)$.

**Почему.** Объекты проходят чётко определённые стадии. Не все переходы допустимы. Конечный автомат формализует множество допустимых переходов и запрещает недопустимые — встроенная валидация.

**Структура:** таблица переходов $\delta[state][event] \to state'$, lookup $O(1)$.

### 4.4. Каузальный порядок событий

**Функциональность:** порядок сообщений в чате.

**Математическая модель:** частичный порядок, логические часы Лэмпорта.

**Почему.** В распределённой системе нет единого времени. Лэмпорт (1978): логический счётчик гарантирует — если $a$ причинно предшествует $b$, то $L(a) < L(b)$. Обратное не гарантируется (Lamport clock — частичный, не тотальный порядок). Для чата двух участников достаточно одного целого числа.

**Алгоритм:**

```
Отправка:    t ← t + 1; прикрепить t к сообщению
Получение:   t ← max(t, t_remote) + 1
Инициализация (восстановление после перезагрузки):
             t ← max(0, max{ lamportTs : m ∈ всех известных сообщений }) + 1
```

**Хранение локального состояния часов.** Lamport clock — singleton-объект в IndexedDB (таблица `clock`, ключ `'lamport'`, значение — целое число). Записывается атомарно вместе с каждым новым отправляемым/принимаемым сообщением (одна транзакция Dexie). При старте приложения значение восстанавливается процедурой инициализации выше, чтобы исключить откат счётчика после очистки кэша или ошибки записи.

**Важно:** `created_at` поля Nostr-событий вида Gift Wrap (kind 1059) намеренно рандомизируются для защиты метаданных (NIP-59). Lamport timestamp хранится **внутри зашифрованного содержимого** (поле `lamportTs` в rumor), а не в `created_at` оболочки.

**Расширение NIP-17.** Ugolok добавляет в JSON-тело rumor (kind 14) кастомное поле `lamportTs: number`. Совместимость в одну сторону: сторонние NIP-17 клиенты увидят сообщение и проигнорируют поле, упорядочив по своему усмотрению; Ugolok при получении rumor без `lamportTs` подставляет 0.

**Тотальный порядок** (для детерминированного UI): при равных `lamportTs` тайбрейкер — лексикографический порядок pubkey отправителя:

$$order(m_1, m_2) = (lamportTs_{m_1}, pubkey_{m_1}) < (lamportTs_{m_2}, pubkey_{m_2})$$

### 4.5. Криптография

**Функциональность:** идентификация, подпись, шифрование, целостность.

**Математическая модель:** циклическая группа $E(\mathbb{F}_p)$ на secp256k1, ECDH, Schnorr (BIP-340), ChaCha20-Poly1305, SHA-256, HKDF.

**Почему secp256k1 и Schnorr.** Определено протоколом Nostr — внешнее ограничение. Безопасность — гипотеза ECDLP. NIP-44 определяет схему: ECDH → HKDF → ChaCha20 → HMAC.

**Деривация ключа из мнемоники (NIP-06).** Трёхэтапный процесс:

1. BIP-39: `mnemonic → seed` (PBKDF2-HMAC-SHA512, 512 бит)
2. BIP-32: `seed → HD master key`
3. BIP-32 derivation: `master → child` по пути `m/44'/1237'/0'/0/0` (Nostr SLIP-44 coin type = 1237)
4. Результат: `child.privateKey` — 32 байта secp256k1 приватного ключа

Это обеспечивает совместимость с любым Nostr-клиентом, реализующим NIP-06.

**ID события (NIP-01):** детерминированный хеш от всего события, не только содержимого:

$$id = SHA\text{-}256\big(UTF8(JSON([0, pubkey, created\_at, kind, tags, content]))\big)$$

Правила сериализации: без пробелов и переносов строк, специальные символы экранированы. **Каждое входящее событие проверяется на соответствие `id` канонической форме перед проверкой подписи** (см. F-EV-01).

### 4.6. Синхронизация

**Функциональность:** синхронизация между устройствами одного пользователя, доставка событий между пользователями, работа при нестабильном соединении.

**Математическая модель:** G-Set — grow-only set (CRDT).

**Почему.** Каждое событие имеет уникальный `id` = SHA-256 от канонической формы события (pubkey + created_at + kind + tags + content). Синхронизация = объединение ($\cup$) множеств событий. Свойства объединения: коммутативность ($A \cup B = B \cup A$), ассоциативность, идемпотентность ($A \cup A = A$). Эти три свойства образуют join-semilattice — достаточное условие для CRDT с гарантированной сходимостью. Специальных CRDT-библиотек не требуется.

**Следствие для мультиустройства.** Два устройства подключены к одному relay. Каждое публикует события и получает события другого. G-Set merge: новые — добавить, уже есть — пропустить. Состояние сходится к одному и тому же независимо от порядка и повторов.

### 4.7. Шифрование блога (Group Key Distribution)

**Функциональность:** шифрование контента блога симметричным ключом; раздача ключа авторизованным читателям без центрального сервера.

**Математическая модель:** гибридное шифрование с версионированными ключами — симметричный ключ блога каждой эпохи, зашифрованный через ECDH для каждого авторизованного pubkey.

**Схема:**

1. **Создание блога:** владелец генерирует `blogKey[v=1]` — 32 случайных байта (симметричный ключ эпохи 1).
2. **Шифрование контента:** каждый пост/комментарий зашифрован ключом текущей эпохи `blogKey[v_current]`. В заголовке зашифрованного сообщения хранится номер эпохи.
3. **Раздача ключа:** при назначении права VIEW создаётся событие kind 30053 с **версионированным d-tag** `{blog_id}:{reader_pubkey}:{key_version}`, в котором `blogKey[v]` зашифрован через NIP-44 ECDH для конкретного pubkey получателя. Поскольку d-tag включает версию, новые ключи **не затирают** старые на relay — каждый читатель сохраняет доступ ко всем эпохам, на которые ему был выдан ключ.
4. **Получатель:** скачивает все kind 30053 с `#p: [его pubkey]`, расшифровывает все доступные `blogKey[v]` своим приватным ключом, при чтении поста выбирает ключ нужной эпохи по заголовку.

**Отзыв доступа:** при удалении права VIEW владелец увеличивает `v_current ← v_current + 1`, генерирует новый `blogKey[v_current]`, публикует kind 30053 для всех **оставшихся** читателей с новой версией. Бывший читатель сохраняет доступ к контенту эпох $\leq v_{revoke}$ (старые kind 30053 на него остаются на relay), но не получает ключ новой эпохи. Новый контент шифруется только новым ключом и недоступен бывшему читателю — даже после холодного старта.

**Семантика безопасности:**

- Forward secrecy от пассивного relay: контент, зашифрованный `blogKey[v]`, недоступен relay даже при выдаче `blogKey[v+1]`.
- Backward secrecy: **не гарантируется**. Бывший читатель сохраняет доступ к контенту своих эпох. Это компромисс: альтернатива — полное перешифрование архива при каждом отзыве, что неприемлемо по производительности.

**Структуры данных:**

| Объект                             | Структура                                                                       | Алгоритм                                         |
| ---------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------ |
| Blog Key (одной эпохи)             | 32 байта (ChaCha20 ключ)                                                        | Генерация: `crypto.getRandomValues(32)`          |
| Зашифрованный blogKey для читателя | kind 30053, d-tag = `{blogId}:{reader}:{v}`, content = NIP-44(blogKey)          | ECDH shared secret + ChaCha20                    |
| Зашифрованный контент поста        | kind 30061, content = `[v_uint32 ‖ ChaCha20-Poly1305(text, blogKey[v], nonce)]` | Префикс версии 4 байта + симметричное шифрование |

| 1059  | NIP-59 | Gift Wrap (внешний слой DM) | NIP-44, эфемерный ключ           | Журнальное  |

**Примечание о NIP-17 (Private Direct Messages):** Приложение реализует полный стек NIP-17:

- Сообщение (rumor, kind 14) — неподписанное, шифруется на уровне seal. **Расширение Ugolok:** дополнительное поле `lamportTs: number` в JSON rumor (см. 4.4)
- Seal (kind 13) — подписан автором, зашифрован NIP-44 для получателя
- Gift Wrap (kind 1059) — подписан эфемерным ключом, содержит seal, зашифрован для получателя
- Sender сохраняет копию: отдельный Gift Wrap (kind 1059) для своего pubkey

### 8.2. Кастомные (приложение-специфичные)

| Kind  | Назначение              | Шифрование                   | Адресат             | d-tag                           | Тип            |
| ----- | ----------------------- | ---------------------------- | ------------------- | ------------------------------- | -------------- |
| 30050 | Группа контактов        | NIP-44 для себя              | Только владелец     | UUID группы                     | State-snapshot |
| 30051 | Правило доступа         | NIP-44 для себя              | Только владелец     | `{subject}:{resource}`          | State-snapshot |
| 30053 | Ключ блога для читателя | NIP-44 (владелец → читатель) | Владелец + читатель | `{blog_id}:{reader_pubkey}:{v}` | State-snapshot |
| 30060 | Блог (метаданные)       | Нет                          | Публичный           | UUID блога                      | State-snapshot |
| 30061 | Пост в блоге            | Blog Key (ChaCha20-Poly1305) | Владельцы Blog Key  | `{blog_id}:{post_id}`           | State-snapshot |
| 30062 | Комментарий             | Blog Key (ChaCha20-Poly1305) | Владельцы Blog Key  | `{post_id}:{comment_id}`        | State-snapshot |
| 30070 | Статус «прочитано»      | NIP-44 для себя              | Только владелец     | chat_id                         | State-snapshot |

Редактирование комментария = публикация нового события с тем же d-tag; relay затрёт предыдущее. Materialized view `comments` делает upsert по `(authorPubkey, commentId)`. История правок не сохраняется (принято для MVP).

## 9. Конечные автоматы

### 9.1. Автомат сообщения

Статус `delivered` исключён из MVP: Nostr не предоставляет встроенного механизма подтверждения доставки. Читаемость (read) — единственный подтверждаемый финальный статус через kind 30070.

```
States:    {created, sending, sent, read, failed, discarded}
Events:    {SEND, ACK, READ, FAIL, RETRY, DISCARD}
Initial:   created
Final:     {read, discarded}

Transitions:
  created   + SEND    → sending
  sending   + ACK     → sent        // relay принял событие (OK message)
  sending   + FAIL    → failed
  sent      + READ    → read        // получатель опубликовал kind 30070
  failed    + RETRY   → sending
  failed    + DISCARD → discarded

Таблица переходов δ[state][event]:
             SEND      ACK     READ    FAIL    RETRY   DISCARD
created    [ sending   —       —       —       —       —       ]
sending    [ —         sent    —       failed  —       —       ]
sent       [ —         —       read    —       —       —       ]
read       [ —         —       —       —       —       —       ] // terminal
failed     [ —         —       —       —       sending discarded]
discarded  [ —         —       —       —       —       —       ] // terminal
```

### 9.2. Автомат поста

```
States:    {draft, published, archived}
Events:    {PUBLISH, ARCHIVE, UNPUBLISH}
Initial:   draft
Final:     {archived}

Transitions:
  draft     + PUBLISH   → published
  published + ARCHIVE   → archived
  published + UNPUBLISH → draft      // возврат в черновик

Таблица переходов δ[state][event]:
             PUBLISH   ARCHIVE   UNPUBLISH
draft      [ published —         —         ]
published  [ —         archived  draft     ]
archived   [ —         —         —         ] // terminal
```

### 9.3. Автомат соединения с relay

```
States:    {disconnected, connecting, connected, connecting_sub, subscribed}
Events:    {CONNECT, OPEN, SUBSCRIBE, SUBSCRIBE_OK, SUBSCRIBE_ERROR,
            CLOSE, ERROR, TIMEOUT}
Initial:   disconnected
Final:     ∅ (не завершается)

Transitions:
  disconnected   + CONNECT          → connecting
  connecting     + OPEN             → connected
  connecting     + ERROR            → disconnected
  connecting     + TIMEOUT          → disconnected
  connected      + SUBSCRIBE        → connecting_sub
  connecting_sub + SUBSCRIBE_OK     → subscribed
  connecting_sub + SUBSCRIBE_ERROR  → connected         // retry subscribe
  connected      + CLOSE            → disconnected
  connected      + ERROR            → disconnected
  connecting_sub + CLOSE            → disconnected
  connecting_sub + ERROR            → disconnected
  subscribed     + CLOSE            → disconnected
  subscribed     + ERROR            → connected         // relay закрыл подписку, переподписаться

Таблица переходов δ[state][event]:
                  CONNECT  OPEN      SUBSCRIBE       SUBSCRIBE_OK SUBSCRIBE_ERROR CLOSE         ERROR
disconnected    [ conn.    —         —               —            —               —             —           ]
connecting      [ —        connected —               —            —               disconnected  disconnected]
connected       [ —        —         connecting_sub  —            —               disconnected  disconnected]
connecting_sub  [ —        —         —               subscribed   connected       disconnected  disconnected]
subscribed      [ —        —         —               —            —               disconnected  connected   ]
```

## 10. Схема базы данных

```javascript
db.version(1).stores({
	// ═══ Event Store (append-only log) ═══
	events: "++seq, id, [pubkey+kind], created_at, *tags",
	//   id     — SHA-256([0,pubkey,created_at,kind,tags,content])
	//   *tags  — multi-entry index на отдельные значения тегов (#p, #e, #d)

	// ═══ Materialized Views ═══
	contacts: "[owner+pubkey], owner",
	groups: "[owner+id], owner",
	groupMembers: "[groupId+pubkey], groupId",
	permissions: "[owner+subject+resource], owner, subject, resource",
	effectivePerms: "[user+resource], user",
	//   кэш: (user, resource) → {allow_mask, deny_mask, effective_mask}
	//   user может быть произвольным subject (см. F-AU-08), не только текущим
	blogKeys: "[blogId+keyVersion], blogId, [blogId+readerPubkey+keyVersion]",
	//   хранит расшифрованные blogKey всех известных эпох
	blogKeyCurrent: "blogId",
	//   blogId → {currentVersion: int}

	// ═══ Сообщения ═══
	messages: "++seq, [chatId+lamportTs+senderPubkey], chatId, id, status",

	// ═══ Контент ═══
	posts: "id, [blogId+created_at], blogId, author, keyVersion",
	comments: "[authorPubkey+commentId], postId, parentId, keyVersion",
	//   upsert по (authorPubkey, commentId) — соответствует replaceable семантике kind 30062

	// ═══ Крипто ═══
	sessions: "[localPub+remotePub]",
	keystore: "id",

	// ═══ Lamport clock ═══
	clock: "id",
	//   id='lamport' → {value: int}
	//   обновляется атомарно вместе с записью messages в одной транзакции

	// ═══ Sync metadata ═══
	syncState: "relay",
	//   relay → {lastSeen: timestamp}
});
```

**Индексная стратегия:**

```javascript
events.where("*tags").equals(["p", myPubkey]);
events.where("[pubkey+kind]").equals([authorPubkey, 30050]);
events.where("created_at").above(lastSeen);
```

## 12. Процедуры жизненного цикла

### 12.1. Онбординг (первый запуск)

```
Вариант A: «Создать аккаунт»
  1. generateMnemonic() → 12 слов (BIP-39, 128 бит энтропии)
  2. Отобразить слова, потребовать подтверждение (ввести повторно)
  3. mnemonicToPrivateKey(words):
       a. seed ← bip39.mnemonicToSeed(words)
       b. root ← bip32.fromSeed(seed)
       c. child ← root.derivePath("m/44'/1237'/0'/0/0")
       d. return child.privateKey
  4. schnorr.getPublicKey(privKey) → pubKey
  5. Запросить пароль для шифрования ключа на устройстве
  6. encryptAndStore(privKey, password):
       a. salt ← crypto.getRandomValues(16)
       b. keyMaterial ← PBKDF2(password, salt, 600000, SHA-256)
       c. encKey ← AES-GCM derive
       d. ciphertext ← AES-GCM.encrypt(privKey, encKey, iv)
       e. store {salt, iv, ciphertext} → IndexedDB keystore
  7. Опубликовать kind 0 (профиль) и kind 10002 (relay list)
  8. Инициализировать lamport clock = 1, записать в IndexedDB
  9. → Основной экран

Вариант B: «Войти по мнемонике»
  1. Пользователь вводит 12 слов
  2. validateMnemonic(words) — проверка чексуммы BIP-39
  3. mnemonicToPrivateKey(words)
  4. schnorr.getPublicKey(privKey) → pubKey
  5. Запросить пароль
  6. encryptAndStore(privKey, password)
  7. → Холодный старт

Вариант C: «Войти по nsec»
  1. nip19.decode(nsec) → privKey
  2. Далее как B.4–B.7
```

### 12.2. Холодный старт

```
coldStart(pubkey, relayList):
  1. Подключиться ко всем relay из relayList
  2. Подписаться на события:
     - {authors: [pubkey]}
     - {'#p': [pubkey]}
     - {authors: [pubkey], kinds: [10002]}
     - {authors: [pubkey], kinds: [30050,30051,30053,30060,30061,30062,30070,30071,30072]}
  3. Получать события батчами по 100 (или раз в 200мс):
     a. Для каждого: validateEventId → verify (в crypto.worker)
     b. G-Set merge (skip если hasEvent(id))
     c. Bulk insert в IndexedDB events одной транзакцией
     d. UI: «Синхронизация: N событий»
  4. После EOSE на всех relay:
  5. Расшифровать приватные события (kinds 30050–30072) для себя
  6. Расшифровать входящие DM (kind 1059): unwrap → rumor → извлечь lamportTs
  7. Расшифровать Blog Keys (kind 30053, '#p': [pubkey]):
     - сгруппировать по blogId
     - для каждой версии: decrypt → blogKeys таблица
     - определить currentVersion = max(v) для каждого blogId
  8. fold(events) → state:
     - Журнальные: упорядочить по (lamportTs, senderPubkey), применить все
     - State-snapshot: для каждого (kind, d-tag) взять latest по created_at
  9. Построить materialized views (контакты, группы, права, blogKeys, ...)
  10. Восстановить lamport clock:
      lamport.value ← max(0, max{m.lamportTs : m ∈ messages}) + 1
      Записать в IndexedDB clock
  11. Полный пересчёт кэша effectivePerms
  12. Записать syncState.lastSeen
  13. → Готово, отрисовать UI
```

### 12.3. Инкрементальная синхронизация

```
incrementalSync(pubkey, relayList):
  1. Для каждого relay получить lastSeen
  2. Подписаться с {since: lastSeen, ...}
  3. Получить новые события (с тем же batching+verify в worker)
  4. Для каждого:
     a. validate → G-Set merge → store
     b. Расшифровать если нужно
     c. fold → update materialized views
     d. Если событие меняет permissions/groups — rebuildCache
     e. Если событие — сообщение — lamport.receive(remoteTs), persist
     f. Emit сигнал → UI
  5. Обновить syncState.lastSeen
```

### 12.4. Отправка сообщения (NIP-17)

```
sendMessage(text, recipientPubkey, privKey):
  1. lamportTs ← lamport.tick()  // и атомарно persist в IndexedDB
  2. rumor ← {
       kind: 14,
       pubkey: myPubkey,
       created_at: now(),
       content: text,
       lamportTs,                  // расширение Ugolok
       tags: [['p', recipientPubkey]]
     }
  3. // Gift Wrap для получателя
     seal_for_recipient ← sign({
       kind: 13,
       content: NIP44.encrypt(JSON(rumor), privKey, recipientPubkey),
       created_at: randomTimestamp(-2days..now),
       pubkey: myPubkey
     }, privKey)
     giftWrap_for_recipient ← sign({
       kind: 1059,
       content: NIP44.encrypt(JSON(seal_for_recipient), ephKey, recipientPubkey),
       created_at: randomTimestamp(-2days..now),
       pubkey: ephPubkey,
       tags: [['p', recipientPubkey]]
     }, ephKey)
  4. // Gift Wrap для себя (одной копии достаточно для всех своих устройств)
     seal_for_self, giftWrap_for_self — аналогично, но на myPubkey
  5. Сохранить в messages + events (одна транзакция с lamport persist)
  6. Опубликовать оба gift wrap (или в outbox)
  7. messageMachine.send({type: 'SEND'}) → sending
  8. ACK от relay → sent;  ERROR → failed
```

### 12.5. Создание блога и предоставление доступа

```
createBlog(name, description, privKey):
  1. blogId ← UUID()
  2. blogKey[1] ← crypto.getRandomValues(32)
  3. blogKeyCurrent[blogId] ← {currentVersion: 1}
  4. Опубликовать kind 30060 {tags: [['d', blogId]], content: JSON({name, description})}
  5. Сохранить blogKey[1] локально
  6. Зашифровать blogKey[1] для себя: kind 30053, d-tag = `{blogId}:{myPubkey}:1`

grantBlogAccess(blogId, readerPubkey, privKey):
  1. v ← blogKeyCurrent[blogId].currentVersion
  2. blogKey ← getBlogKey(blogId, v)
  3. encryptedKey ← NIP44.encrypt(blogKey, privKey, readerPubkey)
  4. Опубликовать kind 30053:
     { kind: 30053,
       content: encryptedKey,
       tags: [['d', `${blogId}:${readerPubkey}:${v}`], ['p', readerPubkey]] }

revokeBlogAccess(blogId, revokedPubkey, privKey):
  1. v_new ← blogKeyCurrent[blogId].currentVersion + 1
  2. blogKey[v_new] ← crypto.getRandomValues(32)
  3. blogKeyCurrent[blogId].currentVersion ← v_new
  4. Сохранить blogKey[v_new] локально
  5. Для каждого оставшегося читателя R с правом VIEW:
     - encryptedKey ← NIP44.encrypt(blogKey[v_new], privKey, R)
     - Опубликовать kind 30053 с d-tag = `{blogId}:{R}:{v_new}`
  6. Зашифровать blogKey[v_new] для себя: d-tag = `{blogId}:{myPubkey}:{v_new}`
  7. Опубликовать обновлённый kind 30060 с маркером currentVersion = v_new
  // Старые kind 30053 для revokedPubkey НЕ удаляются — версионированный d-tag
  // не пересекается с новым, поэтому relay не затирает старые ключи.
  // Бывший читатель сохраняет доступ к контенту эпох 1..v_old (см. L-07).

createPost(blogId, text, privKey):
  1. v ← blogKeyCurrent[blogId].currentVersion
  2. blogKey ← getBlogKey(blogId, v)
  3. nonce ← crypto.getRandomValues(12)
  4. ct ← ChaCha20Poly1305.encrypt(text, blogKey, nonce)
  5. payload ← uint32BE(v) ‖ nonce ‖ ct
  6. Опубликовать kind 30061:
     { tags: [['d', `${blogId}:${postId}`], ['blog', blogId]],
       content: base64(payload) }

readPost(event):
  1. payload ← base64Decode(event.content)
  2. v ← uint32BE(payload[0..4])
  3. nonce ← payload[4..16]; ct ← payload[16..]
  4. blogKey ← getBlogKey(blogId(event), v)
  5. text ← ChaCha20Poly1305.decrypt(ct, blogKey, nonce)
```

## 13. План разработки

План разбит на **6 фаз**. Каждая фаза автономна (даёт работающий артефакт) и завершается явным критерием приёмки. Внутри фазы — пронумерованный список действий.

### 13.1. Зависимости фаз

```
Фаза 1 (Фундамент) → Фаза 2 (Идентичность + Crypto)
                  → Фаза 3 (Транспорт + Sync)
                                              → Фаза 4 (Граф доступа)
                                                                   → Фаза 5 (Сообщения)
                                                                                       → Фаза 6 (Контент + UI)
```

Фазы 4 и 5 могут идти частично параллельно после завершения фазы 3 (граф доступа не нужен для базового чата 1-на-1, нужен для блогов в фазе 6).

## 14. Ограничения и допущения

### 14.1. Ограничения

| ID   | Ограничение                                                                                                                                                                                                                                                                                                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------ |
| L-01 | Потеря мнемоники = потеря аккаунта. Нет способа восстановить ключ без мнемоники                                                                                                                                                                                                                                                                                     |
| L-02 | Relay может удалить события. Для надёжности использовать несколько relay. State-snapshot события (30000–39999) relay хранит только последнее на (pubkey, kind, d-tag) — история изменений групп/прав не воспроизводится с relay                                                                                                                                     |
| L-03 | Без Double Ratchet (MVP) компрометация ключа раскрывает историю сообщений                                                                                                                                                                                                                                                                                           |
| L-04 | Права применяются локально. Защита — шифрование: без Blog Key контент недоступен                                                                                                                                                                                                                                                                                    |
| L-05 | Холодный старт зависит от доступности relay и объёма данных                                                                                                                                                                                                                                                                                                         |
| L-06 | Мнемоника BIP-39 + NIP-06 обеспечивает совместимость со стандартными Nostr-клиентами. Если NIP-06 изменит путь деривации — потребуется миграция                                                                                                                                                                                                                     |
| L-07 | **Отзыв доступа к блогу:** бывший читатель сохраняет доступ к контенту эпох, ключи которых он успел получить (старые kind 30053 для него остаются на relay благодаря версионированному d-tag). Контент новых эпох ему недоступен. Backward secrecy не гарантирована — это компромисс с производительностью (альтернатива — перешифрование архива при каждом отзыве) |
| L-08 | NIP-59 рандомизирует created_at gift wrap событий. Временны́е метки сообщений ненадёжны — используется Lamport clock из зашифрованного контента                                                                                                                                                                                                                      |
| L-09 | NIP-17 удваивает исходящий трафик (gift wrap для получателя + для себя). Ёмкость одного gift wrap «для себя» достаточна для всех собственных устройств — pubkey один на пользователя                                                                                                                                                                                |
| L-10 | Инвалидация кэша прав в MVP — полный пересчёт. При $                                                                                                                                                                                                                                                                                                                | permissions | > 10^4$ это становится заметным; гранулярная инвалидация — в backlog 1.2 |
| L-11 | Редактирование комментариев (kind 30062 — replaceable) не сохраняет историю правок                                                                                                                                                                                                                                                                                  |

```javascript
import * as bip39 from "@scure/bip39";
import { wordlist } from "@scure/bip39/wordlists/english";
import { HDKey } from "@scure/bip32";
import { schnorr } from "@noble/curves/secp256k1";

// Тестовый вектор из NIP-06
const mnemonic =
	"leader monkey parrot ring guide accident before fence cannon height naive bean";
const seed = await bip39.mnemonicToSeed(mnemonic);
const root = HDKey.fromMasterSeed(seed);
const child = root.derive("m/44'/1237'/0'/0/0");
const privKey = child.privateKey;
const pubKey = schnorr.getPublicKey(privKey);

// Ожидаемые значения из NIP-06:
// privKey (hex): 7f7ff03d123792d6ac594bfa67bf6d0c0ab55b6b1fdb6249303fe861f1ccba9a
// pubKey  (hex): 17162c921dc4d2518f9a101db33695df1afb56ab82f5ff3e5da6eec3ca5cd917
console.assert(
	Buffer.from(privKey).toString("hex") ===
		"7f7ff03d123792d6ac594bfa67bf6d0c0ab55b6b1fdb6249303fe861f1ccba9a",
);
```
