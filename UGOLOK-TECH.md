## 0. Изменения относительно v4

Документ переработан после внутреннего review v4. Ключевые правки:

**Безопасность и протокол:**

1. Введена криптографическая верификация авторов комментариев в каналах (kind 30054 — подписанный владельцем allowlist), без чего `COMMENT` ≠ `VIEW` не enforced'ится в принципе.
2. d-tag'и приватных state-snapshot событий (30051, 30053, 30054) обфусцированы через HMAC от мастер-секрета владельца — relay больше не видит граф «owner → subject → resource» в открытом виде.
3. Тотальный порядок сообщений расширен тайбрейкером по `eventId` для случая мульти-устройство одного пользователя.
4. Inline-голосовые сообщения ограничены 32 KB raw (с расчётом под лимит NIP-44 v2 plaintext = 65535 байт + тройной wrap).
5. Локальная БД шифруется на устройстве (раньше: только приватный ключ).
6. Терминология forward/backward/post-compromise secrecy переписана корректно (§ 4.7).

**Cold start и масштабирование:**

7. Холодный старт двухфазный: bootstrap (профиль, контакты, права, ключи каналов) + lazy-load (сообщения и контент каналов по требованию). NF-09 переписан под реалистичные сетевые лимиты.
8. NF-13 (потолки) подняты до 100 000 сообщений, 1000 контактов, 100 каналов.
9. Cold-start фильтры дополнены подпиской на 30061/30062 чужих авторов через `#channel` для каналов, где пользователь — читатель.

**Архитектура:**

10. XState v5 удалён; четыре простых ДКА реализуются вручную (~30–50 LOC каждый), бюджет бандла высвобождает 16 KB gzip.
11. Default-список relay задаётся build-time константой; решена chicken-and-egg на онбординге.
12. Деление по фазам пересмотрено: fold для каждого kind поднят в свою фазу; критерии приёмки приведены в соответствие с реальным состоянием системы по фазам.

**LWW и часы:**

13. Чётко разделены G-Set (для журнальных kind 1059) и LWW-Register (для replaceable). Тайбрейкер LWW при равном `created_at` — лексикографический `eventId`.
14. Lamport persist описан непротиворечиво: tick — in-memory, persist — в одной транзакции Dexie с записью события.

**Прочее:**

15. Удаление событий (NIP-09) включено в MVP.
16. Service Worker имеет описанную стратегию обновления (skipWaiting + clients.claim, версионированный cache).
17. Self-hostable определён честно: каждый инстанс — изолированный остров, федерации нет.

## 1. Назначение и область применения

### 1.1. Назначение

Ugolok — приватный мессенджер с публикациями и каналами, построенный на протоколе Nostr поверх **закрытого relay**. Приложение реализует:

- защищённый обмен сообщениями (DM),
- ведение каналов с гранулярным контролем доступа (посты, комментарии),
- передачу вложений через Blossom,
- управление контактами, группами и правами.

### 1.2. Ключевые свойства

- **Замкнутый остров.** Один экземпляр Ugolok = один relay + один (или несколько) Blossom + клиенты. NIP-42 AUTH на входе, whitelist по pubkey. **Федерации между разными экземплярами Ugolok нет** (намеренно). Self-hosting = поднять свой остров для своих пользователей. Несовместимость с публичной экосистемой Nostr — намеренное архитектурное решение.
- **Приватность контента.** Содержимое DM, каналов, прав, настроек зашифровано NIP-44 / ChaCha20-Poly1305. Relay имеет доступ только к шифротексту и к «routing-метаданным» (см. § 1.3).
- **Локальная БД зашифрована.** Расшифрованные материализованные вью на диске защищены ключом, производным от пароля. Без пароля содержимое устройства не читается.
- **Мультиустройство.** Пользователь входит на любом устройстве по мнемонике BIP-39 и видит единое состояние.
- **Автономность.** Работа офлайн после первой загрузки. Синхронизация при появлении сети.
- **Self-hostable.** Любой может поднять собственный экземпляр острова по инструкции.

### 1.3. Что относительно relay является приватным, а что — нет

Честная граница приватности (отсюда — формулировка NF-02):

| Видит relay                                                        | Не видит relay                               |
| ------------------------------------------------------------------ | -------------------------------------------- |
| Pubkey подключённого клиента (через NIP-42)                        | Содержимое DM и постов                       |
| Факт «pubkey A отправил kind 1059 с тегом `#p: B`» (метаданные DM) | Текст сообщений                              |
| Объём трафика и временные интервалы                                | Имена контактов и групп                      |
| Факт «pubkey подписан на тег `#channel: <opaque-id>`»              | Правила доступа (kind 30051, d-tag — HMAC)   |
| Время онлайна                                                      | Состав читателей канала (d-tag 30053 — HMAC) |
| Факт «kind 30053 адресован `#p: X`» (т.е. X получает чьи-то ключи) | Какому именно каналу принадлежит ключ        |

NF-02 формулируется по этой границе.

### 1.4. Целевая платформа

**Клиент:** одностраничное web-приложение, разворачиваемое как пара файлов (`index.html` + `service-worker.js`) на статическом хостинге с HTTPS. Поддержка: Chrome 100+, Firefox 100+, Safari 15.4+. После первой загрузки работает офлайн.

**Серверная часть (вне периметра данного ТЗ):**

- Nostr relay (`strfry` или `nostr-rs-relay`) с NIP-42 AUTH и whitelist по pubkey.
- Blossom server для хранения зашифрованных вложений.
- Hosting для статических файлов клиента.

### 1.5. Контекст переработки

Предыдущая итерация (v3, в эксплуатации) использовала собственный протокол поверх HTTP к Yandex Cloud Functions с Redis. Причины отказа: стоимость и vendor lock-in, неподходящий backend для blob'ов (Redis), дублирование Nostr собственным протоколом, разрастание UI-логики через WebComponents.

## 2. Глоссарий

| Термин                          | Определение                                                                                                                                                                                                 |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Событие (Event)**             | Неизменяемая запись о действии пользователя, подписанная криптографическим ключом автора. `id = SHA-256(JSON([0, pubkey, created_at, kind, tags, content]))` в канонической сериализации (NIP-01)           |
| **Relay**                       | Промежуточный сервер: хранит и пересылает события. В Ugolok — контролируемый владельцем экземпляра, NIP-42 AUTH                                                                                             |
| **Keypair**                     | Пара криптографических ключей secp256k1                                                                                                                                                                     |
| **Мнемоника (NIP-06)**          | 12 слов BIP-39, из которых через BIP-32 (`m/44'/1237'/0'/0/0`) детерминированно выводится приватный ключ                                                                                                    |
| **Master Secret**               | 32 байта, производные от приватного ключа: `HKDF-SHA256(privKey, salt="Ugolok/v1/master", info="")`. Используется для HMAC-обфускации d-tag'ов и для деривации DB-ключа. **Никогда не покидает устройство** |
| **DB Key**                      | 32 байта, `HKDF-SHA256(masterSecret, salt="Ugolok/v1/db", info="")`. Ключ шифрования материализованных вью в IndexedDB                                                                                      |
| **Event Store**                 | Локальное хранилище событий (IndexedDB через Dexie). События хранятся **как есть** (зашифрованные), материализованные вью — отдельно (зашифрованы DB Key)                                                   |
| **Журнальное событие**          | Событие kinds 1000–9999: relay хранит все экземпляры. В Ugolok — gift wrap (kind 1059), kind 5 (deletion)                                                                                                   |
| **State-snapshot событие**      | Событие kinds 30000–39999 (parameterized replaceable): relay хранит только последнее на (pubkey, kind, d-tag). Тайбрейкер при равном `created_at` — лексикографический `eventId`                            |
| **Materialized View**           | Вычисленное представление состояния, полученное свёрткой (`fold`) последовательности событий                                                                                                                |
| **Bootstrap cold start**        | Первая фаза холодного старта: загрузка identity, контактов, прав, ключей каналов. Завершается отрисовкой основных экранов                                                                                   |
| **Lazy load**                   | Дозагрузка данных по требованию: сообщения чата при открытии, посты канала при входе                                                                                                                        |
| **Битовая маска прав (Bitset)** | Целое число, биты которого соответствуют действиям                                                                                                                                                          |
| **G-Set**                       | Grow-only Set — множество, в которое можно только добавлять. Объединение коммутативно, ассоциативно, идемпотентно                                                                                           |
| **LWW-Register**                | Last-Write-Wins — регистр со значением, побеждает запись с большим `(created_at, eventId)`. Тайбрейкер по `eventId` детерминирует исход при равных `created_at`                                             |
| **Lamport Clock**               | Логический счётчик для частичного упорядочивания событий                                                                                                                                                    |
| **d-tag**                       | Тег-идентификатор для parameterized replaceable events                                                                                                                                                      |
| **Opaque d-tag**                | d-tag, полученный как `HMAC-SHA256(masterSecret, "kind:" \|\| logical_key)` — relay видит непрозрачный 32-hex-байтный токен                                                                                 |
| **NIP-XX**                      | См. NIP-01, 02, 06, 09, 17, 19, 42, 44, 59, 65 — соответствующие стандарты протокола Nostr                                                                                                                  |
| **Channel Key**                 | Симметричный ключ канала (32 байта, ChaCha20-Poly1305). Распределяется авторизованным читателям через NIP-44                                                                                                |
| **Key Version**                 | Целочисленный номер поколения Channel Key. Увеличивается при ротации                                                                                                                                        |
| **Channel Topic**               | 16 случайных байт, генерируется при создании канала, используется как routing-tag (`#channel: <topic>`). Не ротируется при revoke                                                                           |
| **Comment Allowlist**           | kind 30054, подписанный владельцем канала список pubkey, которым разрешено комментировать. Шифруется channelKey[v_current] и распространяется всем читателям                                                |
| **Blossom**                     | Спецификация blob-хостинга для Nostr: файлы адресуются SHA-256, авторизация через kind 24242                                                                                                                |

## 3. Архитектура системы

### 3.1. Архитектурные принципы

**Принцип 1. Математика → структуры данных → алгоритмы → инструменты.**

Для ядра приложения (криптография, синхронизация, авторизация, конечные автоматы, каузальный порядок):

1. Сформулировать задачу в терминах чистой математики.
2. Подобрать оптимальные структуры данных.
3. Выбрать или вывести алгоритмы.
4. Выбрать инструменты, реализующие эти алгоритмы наименее искажённо.

Из этого принципа: для четырёх простых ДКА (§ 9) внешняя библиотека (XState и аналоги) **не используется** — ДКА реализуются как `transitions[state][event] → state` в 30–50 LOC каждый. Это и проще, и экономит ~16 KB gzip бандла.

**Принцип 2. UI — чистая проекция состояния.**

UI-компоненты:

- **не содержат** машин состояний, бизнес-логики, прямых обращений к репозиториям, криптографии или транспорту;
- **получают** данные из сигналов domain-слоя;
- **испускают** семантические события (`onSubmitMessage`, `onSelectChat`).

Запрещено: WebComponents с собственным жизненным циклом для бизнес-логики; импорт `core/*` в компоненты.

**Принцип 3. Event Sourcing для синхронизируемого состояния.**

$$State_t = fold(State_0,\; [e_1, e_2, \ldots, e_t])$$

где $e_i$ — подписанное Nostr-событие, $fold$ — детерминированная чистая функция.

**Принцип 4. Гибридная модель событий Nostr.**

| Класс          | Поведение relay                        | Семантика fold                          | Применение в Ugolok                            |
| -------------- | -------------------------------------- | --------------------------------------- | ---------------------------------------------- |
| Журнальные     | Хранит все                             | G-Set merge, упорядочить, применить все | DM (kind 1059), удаления (kind 5)              |
| State-snapshot | Хранит latest на (pubkey, kind, d-tag) | LWW-Register по `(created_at, eventId)` | Группы, права, каналы, посты, allowlist, настр |

История изменений state-snapshot объектов **не воспроизводима с relay**.

## 4. Математические основания

### 4.1. Данные и сущности

**Модель:** конечные множества, бинарные отношения, частично упорядоченные множества (деревья).

| Объект                                      | Структура                                       | Обоснование                                                |
| ------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| Множество с проверкой ∈                     | Hash Set                                        | $O(1)$ проверка                                            |
| Бинарное отношение $R \subseteq A \times B$ | Hash Map: $a \to \mathrm{Set}\langle b \rangle$ | $O(1)$ образ элемента                                      |
| Дерево (комментарии)                        | Parent-указатель + DFS Euler Tour               | $O(1)$ проверка «v потомок u»: $in_u \leq in_v \leq out_u$ |

### 4.2. Авторизация и права доступа

**Модель:** булева алгебра $2^A$, где $A = \{\text{VIEW}, \text{COMMENT}, \text{WRITE}, \text{MODERATE}, \text{ADMIN}\}$ + трёхзначная логика для allow/deny/undefined.

> Замечание: `CHAT` из v4 удалён. Право переписываться с контактом представлено самим присутствием в kind 3 (NIP-02). Дублирующего бита не нужно.

**Изоморфизм** $2^A \cong \{0,1\}^{|A|}$ позволяет выполнять все операции через побитовую арифметику: $\cup = \mathrm{OR}$, $\cap = \mathrm{AND}$, $\setminus = \mathrm{AND\,NOT}$, всё за $O(1)$.

**Кодирование правила:** пара `(allow_mask, deny_mask)`. Эффективные права: `effective = allow & ~deny`.

**Семантика fail-closed:** undefined правило → `0 & ~0 = 0` → denied.

**Алгоритм инвалидации (MVP — полный пересчёт):**

```
on event(kind in {3, 30050, 30051}):
  effectivePerms.clear(owner)
  for each (subject, resource) in permissions(owner):
      mask ← computeEffective(owner, subject, resource)
      effectivePerms.set([owner, subject, resource], mask)
```

При числе правил ≤ 10000 — менее 100 мс на референсном устройстве. Гранулярная инвалидация — backlog.

### 4.3. Состояния объектов

**Модель:** детерминированный конечный автомат $(S, \Sigma, \delta, s_0, F)$.

**Реализация:** таблица переходов $\delta[state][event] \to state'$, lookup $O(1)$. Хэндлеры эффектов задаются отдельно. Без внешней библиотеки. Юнит-тесты: исчерпывающий обход допустимых и недопустимых пар (state, event).

### 4.4. Каузальный порядок событий

**Модель:** частичный порядок, логические часы Лэмпорта (1978), дополненные тайбрейкером по `eventId` для случая мульти-устройство.

**Алгоритм:**

```
Tick (отправка):     t ← t + 1; вернуть t (in-memory)
Receive:             t ← max(t, t_remote) + 1 (in-memory)
Persist:             вместе с записью события в одной транзакции
Init (после fold):   t ← max(0, max{lamportTs : m ∈ messages}) + 1
```

**Хранение:** Lamport clock — singleton-объект в IndexedDB (таблица `clock`, ключ `'lamport'`). Запись в БД происходит **только** в составе транзакции, добавляющей сообщение. In-memory tick без транзакции — допустим (если приложение упало между tick и persist, in-memory значение теряется, при следующем запуске Init корректно восстановит из max{lamportTs}).

**Расположение timestamp в DM.** `created_at` поля Nostr-событий kind 1059 рандомизируются (NIP-59). Lamport timestamp хранится **внутри зашифрованного rumor** в поле `lamportTs: number`. Сторонние NIP-17 клиенты увидят неизвестное поле и проигнорируют его.

**Тотальный порядок** для детерминированного UI:

$$order(m_1, m_2) = (lamportTs_{m_1}, pubkey_{m_1}, eventId_{m_1}) < (lamportTs_{m_2}, pubkey_{m_2}, eventId_{m_2})$$

`eventId` — id внешнего gift wrap (kind 1059), не rumor. Используется как **детерминированный тайбрейкер** на случай, когда два устройства одного пользователя одновременно отправляют сообщения с одинаковым lamportTs и совпадающим pubkey. (`eventId` гарантированно уникален для разных рандомизированных gift wrap'ов.)

**Ограничение MVP:** Lamport clock — единый счётчик на пользователя. Между сообщениями разных чатов это даёт монотонный sequence без причинной связи. Для групповых чатов (backlog) — per-chat clock.

### 4.5. Криптография

**Модель:** циклическая группа $E(\mathbb{F}_p)$ на secp256k1, ECDH, Schnorr (BIP-340), ChaCha20-Poly1305 (AEAD), ChaCha20 + HMAC-SHA256 (NIP-44 v2 — encrypt-then-MAC), SHA-256, HKDF-SHA256.

**Деривация ключа из мнемоники (NIP-06):**

1. BIP-39: `mnemonic → seed` (PBKDF2-HMAC-SHA512, 2048 итераций).
2. BIP-32: `seed → HD master key`.
3. Производная по пути `m/44'/1237'/0'/0/0` → 32 байта secp256k1 privkey.

**Деривация Master Secret и DB Key:**

```
masterSecret = HKDF-SHA256(privKey, salt="Ugolok/v1/master", info="", length=32)
dbKey        = HKDF-SHA256(masterSecret, salt="Ugolok/v1/db", info="", length=32)
```

`masterSecret` живёт в памяти после ввода пароля, не сохраняется на диск. `dbKey` — то же самое.

**ID события (NIP-01):**

$$id = \mathrm{SHA\text{-}256}(\mathrm{UTF8}(\mathrm{JSON}([0, pubkey, created\_at, kind, tags, content])))$$

Сериализация: без пробелов и переносов, специальные символы экранированы. **Каждое входящее событие проверяется на соответствие `id` канонической форме перед проверкой подписи** (см. F-EV-01).

**Шифрование сообщений (NIP-44 v2):** ECDH (secp256k1) → HKDF-SHA256 → ChaCha20 (encrypt) → HMAC-SHA256 (auth, encrypt-then-MAC) + padding до степени двойки. **Жёсткий лимит plaintext: 65535 байт.**

**Шифрование контента каналов:** ChaCha20-Poly1305 (AEAD) с симметричным `channelKey[v]`.

**Шифрование локальной БД (materialized views):** ChaCha20-Poly1305 c `dbKey`. Каждая запись таблицы (например, `messages`, `channels`, `posts`, `comments`, `permissions`, `effectivePerms`) хранится как `{nonce: 12 bytes, ciphertext+tag: bytes}`. Nonce — случайный, новый на каждую запись.

### 4.6. Синхронизация

Различаем два режима в зависимости от kind события.

**Журнальные события (kind 1059, 5)** — **G-Set**:

- коммутативность ($A \cup B = B \cup A$),
- ассоциативность,
- идемпотентность ($A \cup A = A$).

Эти три свойства делают $(\mathcal{P}(\text{Events}), \cup)$ join-semilattice — гарантированная сходимость.

**State-snapshot события (kind 30000–39999)** — **LWW-Register**:

Для каждого ключа $(pubkey, kind, dtag)$ выбирается значение по правилу:

$$\text{winner}(e_1, e_2) = \begin{cases} e_1 & \text{если } (created\_at_{e_1}, id_{e_1}) > (created\_at_{e_2}, id_{e_2}) \\ e_2 & \text{иначе} \end{cases}$$

Лексикографическое сравнение `id` — детерминированный тайбрейкер при равных `created_at`.

**Следствие.** Два устройства одного пользователя, подключённые к одному relay, через комбинированный (G-Set ∪ LWW) merge сходятся к идентичному состоянию.

**Допущение по часам:** при расхождении часов между двумя устройствами одного пользователя более чем на 60 секунд возможна аномалия LWW (более позднее по wall-clock изменение проигрывает). Митигация — клиент при старте проверяет своё время через relay (`NEGENTROPY` или сравнение с `created_at` свежих событий) и предупреждает пользователя при расхождении > 30 секунд.

### 4.7. Шифрование канала и контроль доступа

**Функциональность:** шифрование контента канала симметричным ключом; раздача ключа авторизованным читателям; **криптографически проверяемая** проверка авторизации комментаторов.

#### 4.7.1. Channel Key Distribution

**Схема:**

1. **Создание канала:** владелец генерирует `channelKey[v=1]` — 32 случайных байта, и `channelTopic` — 16 случайных байт.
2. **Шифрование контента:** пост/комментарий зашифрован `ChaCha20-Poly1305(text, channelKey[v_current], nonce)`. В заголовке payload — номер эпохи.
3. **Раздача ключа:** при назначении VIEW создаётся kind 30053 с d-tag = `HMAC-SHA256(masterSecret, "30053:" || channelId || readerPubkey || keyVersion)`. Содержимое — `NIP-44(channelKey[v], ownerPriv, readerPub)`. Тег `#p: [readerPubkey]` для маршрутизации.
4. **Получатель:** скачивает все kind 30053 с `#p: [его pubkey]`, расшифровывает, при чтении поста выбирает ключ по эпохе из заголовка.

**Отзыв доступа:** `v_current ← v_current + 1`, новый `channelKey`, новый `Comment Allowlist` (см. § 4.7.2), публикация kind 30053 для оставшихся читателей с новой версией.

**Семантика безопасности (корректная терминология):**

- **Post-compromise security:** после revoke и ротации ключа, новый контент канала **недоступен** бывшему читателю (он не получает новых kind 30053). ✓
- **Доступ к историческому контенту:** бывший читатель **сохраняет** возможность расшифровать события эпох ≤ v_revoke, которые он успел скачать. Перешифрование архива при каждом revoke — отвергнуто по производительности.
- **Forward secrecy** в строгом смысле (компрометация долгосрочного ключа не раскрывает прошлых сессий): **не предоставляется**. Долгосрочный приватный ключ позволяет расшифровать все свои kind 30053, что даёт все channelKey. Это приемлемо для MVP; полная FS — backlog (Double Ratchet, §13.10).
- **Privacy от пассивного relay:** relay видит факт «kind 30053 адресован #p: X» (X получил какой-то ключ канала) и factor versioning через d-tag, но d-tag — opaque HMAC, поэтому связки `(channel, reader, version)` не видны.

#### 4.7.2. Comment Allowlist (kind 30054)

Без этого механизма различение `VIEW` vs `COMMENT` невозможно cryptographically: любой читатель имеет channelKey и может зашифровать произвольный kind 30062.

**Схема:**

1. Владелец канала ведёт список pubkey, которым разрешено комментировать. Список сохраняется как kind 30054:
   ```
   {
     kind: 30054,
     pubkey: ownerPubkey,
     tags: [
       ['d', HMAC(masterSecret, "30054:" || channelId)],
       ['channel', channelTopic]
     ],
     content: ChaCha20-Poly1305(
       JSON({channelId, version: v, allowedAuthors: [pubkey1, pubkey2, ...]}),
       channelKey[v],
       nonce
     )
   }
   ```
2. Подписан владельцем (Schnorr).
3. Зашифрован channelKey[v_current] — все актуальные читатели могут прочесть.
4. При revoke ротируется (новая версия, новый список без удалённого).

**Верификация комментария читателем:**

```
on receive(event of kind 30062):
  1. Расшифровать content channelKey[v] (v из header)
  2. Проверить Schnorr-подпись event.pubkey (стандартная)
  3. Найти actual allowlist[v] (kind 30054 за эпоху v)
  4. Проверить event.pubkey ∈ allowlist[v].allowedAuthors
  5. Проверить allowlist подписан channelOwner (kind 30060.pubkey)
  6. Если хоть один шаг fails → discard, не показывать
```

**Свойства:**

- Малициозный читатель с VIEW не может опубликовать «легитимный» комментарий: его pubkey не в allowlist, владелец его подпись на allowlist'е не клал. Все честные клиенты отбросят его комментарий.
- Малициозный читатель не может подделать allowlist: kind 30054 подписан Schnorr-ключом владельца; малициозный читатель не имеет доступа к этому приватному ключу.
- Relay не enforce'ит ничего, но это и не его роль — enforcement криптографический.

**Стоимость:** дополнительный kind 30054 на канал, обновляется при изменении прав COMMENT. ~0.5 KB на 100 комментаторов.

### 4.8. Обфускация d-tag

Для kind 30051, 30053, 30054 (приватные state-snapshot, имеющие потенциально чувствительные ключи) d-tag вычисляется как:

```
opaqueDTag(kind, logicalKey) = HMAC-SHA256(masterSecret, kind + ":" + logicalKey).hex
```

Где `logicalKey` для каждого kind:

| kind  | logicalKey                                             |
| ----- | ------------------------------------------------------ |
| 30051 | `subject_pubkey + ":" + resource_id`                   |
| 30053 | `channel_id + ":" + reader_pubkey + ":" + key_version` |
| 30054 | `channel_id + ":" + key_version`                       |

Владелец однозначно вычисляет d-tag (детерминированно) для записи и обновления. Релэй видит непрозрачный 64-hex-символ. Получатель (для kind 30053) находит свои события через `#p: [своя pubkey]` — d-tag не нужно вычислять.

Для kind 30050 (группы) d-tag = UUID группы — оставлено в открытом виде, потому что только владелец читает (filter `authors: [self]`).

Для kind 30060 (channel metadata), 30061 (post), 30062 (comment), 30070, 30071, 30072 d-tag не несёт privacy-чувствительных связок: 30060 — UUID канала; 30061/30062 — `{channelId}:{postId/commentId}`. Относительно channelId всё равно используется `#channel: [channelTopic]` для маршрутизации (channelTopic — opaque 16 байт).

| F-AT-08 | Голосовая запись: MediaRecorder → opus в webm. **Inline в payload — только если raw ≤ 32 KB** (расчёт под лимит NIP-44 v2 plaintext = 65535 байт с учётом base64 + JSON-обёртки + полей rumor). Иначе — через Blossom                                                                         |
| F-AT-09 | Список Blossom-серверов хранится в settings (kind 30072), пользователь может добавить свои                                                                                                                                                                                                    |
| F-AT-10 | Авторизация на Blossom: `PUT/DELETE` требуют kind 24242 с `t=upload/delete`, `expiration`, `x=<sha256>`. **`GET` — без авторизации** (стандартное поведение Blossom; whitelist по pubkey применяется на uploaders, не на readers; readers всё равно не могут расшифровать без ключа из rumor) |

| NF-13 | Автономность        | Работа после первой загрузки без сети до момента синхронизации                                                                         |
| NF-14 | Масштабирование     | 100 000 сообщений, 1000 контактов, 100 каналов на устройстве. IndexedDB размер ≤ 500 MB                                                |

## 9. Конечные автоматы

Реализуются вручную как `transitions[state][event] → state`. Без внешней библиотеки.

### 9.1. Автомат сообщения

```
States:    {created, sending, sent, read, failed, discarded}
Events:    {SEND, ACK, READ, FAIL, RETRY, DISCARD}
Initial:   created
Final:     {read, discarded}

Transitions:
  created   + SEND    → sending
  sending   + ACK     → sent        // OK от relay
  sending   + FAIL    → failed
  sent      + READ    → read        // получен kind 30070
  failed    + RETRY   → sending
  failed    + DISCARD → discarded
```

### 9.2. Автомат поста

```
States:    {draft, published, archived}
Events:    {PUBLISH, ARCHIVE, UNPUBLISH}
Initial:   draft
Final:     {archived}

Transitions:
  draft     + PUBLISH   → published
  published + ARCHIVE   → archived
  published + UNPUBLISH → draft
```

### 9.3. Автомат соединения с relay

```
States:    {disconnected, connecting, authenticating, connected, subscribed}
Events:    {CONNECT, OPEN, AUTH_CHALLENGE, AUTH_OK, AUTH_FAIL,
            SUBSCRIBE_OK, CLOSE, ERROR, TIMEOUT}
Initial:   disconnected

Transitions:
  disconnected     + CONNECT          → connecting
  connecting       + OPEN             → authenticating
  authenticating   + AUTH_CHALLENGE   → authenticating       // отправить 22242
  authenticating   + AUTH_OK          → connected
  authenticating   + AUTH_FAIL        → disconnected
  authenticating   + TIMEOUT          → disconnected
  connected        + SUBSCRIBE_OK     → subscribed
  *                + CLOSE            → disconnected
  *                + ERROR            → disconnected
  subscribed       + ERROR            → connected
```

### 9.4. Автомат transfer (Blossom-загрузка)

```
States:    {idle, encrypting, uploading, completed, failed}
Events:    {START, ENCRYPTED, UPLOADED, ERROR, RETRY}

Transitions:
  idle       + START      → encrypting
  encrypting + ENCRYPTED  → uploading
  uploading  + UPLOADED   → completed
  uploading  + ERROR      → failed
  failed     + RETRY      → encrypting
```

## 10. Схема базы данных

```javascript
db.version(1).stores({
	// ═══ Event Store (append-only log, события Nostr хранятся как есть) ═══
	// Уже зашифрованы protocol-уровнем; dbKey не применяется
	events: "++seq, id, [pubkey+kind], created_at, *flatTags",
	//   *flatTags — мульти-индекс: каждый тег пишется как "p:abc", "channel:topic", "e:eid"

	// ═══ Materialized Views (зашифрованы dbKey, см. § 5.13) ═══
	//   Все таблицы ниже хранят значения как {nonce, ciphertext}; индексы — по plaintext-ключам
	contacts: "[owner+pubkey], owner",
	blockedContacts: "[owner+pubkey], owner",
	groups: "[owner+id], owner",
	groupMembers: "[groupId+pubkey], groupId",
	permissions: "[owner+subject+resource], owner, subject, resource",
	effectivePerms: "[owner+subject+resource], owner, subject, resource",
	channelKeys: "[channelId+keyVersion], channelId",
	channelKeyMeta: "channelId", // {currentVersion}
	channelTopics: "channelId", // {channelId → channelTopic для routing}
	commentAllowlists: "[channelId+keyVersion], channelId", // verified allowlist кэш

	// ═══ Сообщения (зашифрованы dbKey) ═══
	messages:
		"++seq, [chatId+lamportTs+senderPubkey+id], chatId, id, status, deleted",
	//   id — eventId gift wrap'а (для тайбрейкера и идемпотентности)
	//   deleted — boolean, индекс для фильтра «не показывать удалённые»

	// ═══ Контент (зашифровано dbKey) ═══
	channels: "id, owner",
	posts: "id, [channelId+created_at], channelId, author, keyVersion, deleted",
	comments: "[authorPubkey+commentId], postId, parentId, keyVersion, deleted",

	// ═══ Вложения (метаданные; сами файлы на Blossom) ═══
	attachments: "sha256, messageId, type, mime",

	// ═══ Крипто (приватный ключ зашифрован паролем; dbKey не применяется) ═══
	keystore: "id",

	// ═══ Lamport clock (зашифровано dbKey) ═══
	clock: "id", // id='lamport' → {value: int}

	// ═══ Sync metadata (открыто, не sensitive) ═══
	syncState: "relay", // relay → {lastSeen}
	chatSyncState: "chatId", // chatId → {lastSeen}  для lazy-load
	channelSyncState: "channelId", // channelId → {lastSeen}

	// ═══ Outbox (зашифровано dbKey) ═══
	outbox: "++seq, eventId, status, retryCount",

	// ═══ Inbox запросов (зашифровано dbKey) ═══
	inboxRequests: "id, senderPubkey, created_at",

	// ═══ Удаления (для применения NIP-09) ═══
	deletions: "targetId, deleterPubkey, created_at",
});
```

**Замечание о `*flatTags`:** Dexie multi-entry index работает по плоскому массиву строк. Поэтому при insert каждый Nostr-тег `[name, value, ...]` преобразуется в строку `"name:value"` и кладётся в массив `flatTags`. Запрос `events.where("flatTags").equals("p:abc")` найдёт события с тегом `["p", "abc", ...]`.

**Стратегии запросов:**

```javascript
events.where("flatTags").equals(`p:${myPubkey}`);
events.where("[pubkey+kind]").equals([authorPubkey, 30050]);
events.where("created_at").above(lastSeen);
events.where("flatTags").equals(`channel:${channelTopic}`);
```

## 12. Процедуры жизненного цикла

### 12.1. Онбординг

```
Вариант A: «Создать аккаунт»
  1. generateMnemonic() → 12 слов BIP-39
  2. Отобразить, потребовать подтверждение (повторный ввод)
  3. mnemonicToPrivateKey(words) (NIP-06)
  4. pubKey ← schnorr.getPublicKey(privKey)
  5. Запросить пароль для шифрования ключа
  6. encryptAndStore(privKey, password):
       salt ← crypto.getRandomValues(16)
       keyMaterial ← PBKDF2-SHA256(password, salt, 600000)
       encKey ← derive AES-GCM
       iv ← crypto.getRandomValues(12)
       ct ← AES-GCM.encrypt(privKey, encKey, iv)
       store {salt, iv, ciphertext} в keystore
  7. Производство в памяти: masterSecret, dbKey
  8. Подключиться к BUILD_DEFAULT_RELAYS → AUTH (NIP-42)
  9. Опубликовать kind 0 + kind 10002
  10. Lamport clock ← 1
  11. → Основной экран

Вариант B: «Войти по мнемонике»
  1. validateMnemonic(words)
  2. mnemonicToPrivateKey, дальше как A.4–A.7
  3. → Bootstrap cold start

Вариант C: «Войти по nsec»
  1. nip19.decode(nsec) → privKey
  2. Дальше как B.2
```

### 12.2. Bootstrap cold start

```
bootstrap(pubkey, relayList):
  1. Подключиться ко всем relay → NIP-42 AUTH
  2. Subscribe (одной транзакцией REQ):
     - {authors: [pubkey]}                                  // мои события всех kind'ов
     - {'#p': [pubkey], kinds: [30053]}                     // ключи каналов, где я читатель
     # сообщения (kind 1059) и контент каналов (30061/30062) — НЕ в bootstrap, lazy
  3. Получать события батчами (100 / 200 мс):
     a. validateEventId → verifySig (crypto.worker)
     b. G-Set merge (skip если hasEvent(id))
     c. Bulk insert в events одной транзакцией Dexie
     d. UI: «Bootstrap: N событий»
  4. После EOSE на всех relay:
  5. Расшифровать приватные kinds (30050, 30051, 30060, 30070, 30071, 30072 — NIP-44 для себя)
  6. Расшифровать channel keys (kind 30053):
     - decrypt → channelKeys
     - currentVersion = max(v) для каждого channelId
  7. Подгрузить kind 30054 для каждого channelId, у которого мы reader:
     - REQ {kinds: [30054], '#channel': [channelTopic[c]] for each c}
     - Расшифровать channelKey[v]; сохранить в commentAllowlists
  8. fold(events) → materialized views:
     - State-snapshot: для каждого (kind, d-tag) применить LWW (max by (created_at, id))
     - kind 5 (deletions) → пометка target events
  9. Полный rebuild кэша effectivePerms
  10. lamport.value ← max(0, max{m.lamportTs}) + 1; persist
  11. Записать syncState.lastSeen
  12. → Готово, можно навигировать

  Сообщения и контент каналов будут подгружены lazy при открытии.
```

### 12.3. Lazy-load чата

```
openChat(contactPubkey):
  1. lastSeen ← chatSyncState[chatId(contactPubkey)] || 0
  2. REQ {'#p': [pubkey], kinds: [1059], since: lastSeen}
     // Это даст и входящие от contactPubkey, и self-mirror от меня
  3. Для каждого нового события:
     a. unwrap NIP-59 → seal → rumor
     b. Проверка rumor.pubkey == seal.pubkey (F-EV-05)
     c. whitelist: rumor.pubkey ∈ contacts? иначе → inboxRequests
     d. Извлечь lamportTs, attachments, content
     e. encrypt + insert в messages (dbKey)
     f. lamport.receive(rumor.lamportTs); persist
  4. chatSyncState[chatId] ← max(created_at)
  5. Окна по 100 событий при скролле вверх (REQ {since: older, until: window})
```

### 12.4. Lazy-load канала

```
openChannel(channelId):
  1. lastSeen ← channelSyncState[channelId] || 0
  2. topic ← channelTopics[channelId]
  3. REQ {'#channel': [topic], kinds: [30061, 30062, 30054, 5], since: lastSeen}
  4. Для каждого нового события:
     a. validate id + sig
     b. Если kind 30054: F-EV-07, расшифровать, обновить commentAllowlists
     c. Если kind 30061: расшифровать channelKey[v из header], сохранить в posts
     d. Если kind 30062: расшифровать; F-EV-06 (verify allowlist); сохранить в comments (или discard)
     e. Если kind 5: F-EV-08, пометить target deleted
  5. channelSyncState[channelId] ← max(created_at)
```

### 12.5. Инкрементальная синхронизация (фоновая)

```
incrementalSync(pubkey, relayList):
  1. Для каждого relay получить syncState.lastSeen
  2. AUTH (если соединение свежее)
  3. Подписаться с {since: lastSeen, ...} на bootstrap-набор kind'ов
  4. Для каждого нового события:
     a. validate → G-Set merge → store
     b. Расшифровать если нужно
     c. fold → update views (через signals)
     d. Если permissions/groups/contacts → rebuildCache (или гранулярно в backlog)
     e. Если message в открытом chat → lamport.receive; UI update
     f. Если 30054 для открытого channel → обновить allowlist; ре-валидация comments
  5. syncState.lastSeen ← max(created_at)
```

### 12.6. Отправка DM (NIP-17)

```
sendDM(text, attachments[], recipientPubkey, privKey):
  1. ts ← lamport.tick()                       // in-memory only
  2. Для каждого вложения:
     a. fileKey ← crypto.getRandomValues(32)
     b. ct ← ChaCha20-Poly1305(file, fileKey, nonce)
     c. blob ← upload to Blossom (auth event kind 24242)
     d. push {type, sha256, blossomUrl, encryptionKey: fileKey, mime, size, name}
  3. rumor ← {
       kind: 14, pubkey: myPubkey, created_at: now(),
       content: text, lamportTs: ts, attachments,
       tags: [['p', recipientPubkey]]
     }
  4. // Gift Wrap для получателя
     seal_rcp ← sign({
       kind: 13,
       content: NIP44.encrypt(JSON(rumor), privKey, recipientPubkey),
       created_at: random(-2d..now), pubkey: myPubkey
     }, privKey)
     wrap_rcp ← sign({
       kind: 1059,
       content: NIP44.encrypt(JSON(seal_rcp), ephKey, recipientPubkey),
       created_at: random(-2d..now), pubkey: ephPubkey,
       tags: [['p', recipientPubkey]]
     }, ephKey)
  5. // Gift Wrap для себя
     seal_self, wrap_self аналогично, но на myPubkey
  6. ОДНОЙ транзакцией Dexie:
     - events.add(wrap_rcp), events.add(wrap_self)
     - messages.add(messageRecord)               // зашифровано dbKey
     - clock.put({id: 'lamport', value: ts + 1}) // persist
  7. Опубликовать оба wrap (или в outbox при offline)
  8. messageMachine.send({type:'SEND'}) → sending
  9. ACK от relay → sent;  ERROR → failed
```

### 12.7. Жизненный цикл канала

```
createChannel(name, description, privKey):
  1. channelId ← UUID()
  2. channelTopic ← crypto.getRandomValues(16)
  3. channelKey[1] ← crypto.getRandomValues(32)
  4. channelKeyMeta[channelId] ← { currentVersion: 1 }
  5. channelTopics[channelId] ← channelTopic
  6. metadata ← { name, description, channelTopic }
  7. ct ← NIP44.encrypt(JSON(metadata), privKey, myPubkey)
  8. Опубликовать kind 30060 { tags:[['d', channelId]], content: ct }
  9. Опубликовать kind 30053 для себя:
       d-tag = HMAC(masterSecret, "30053:" + channelId + ":" + myPubkey + ":1")
       content = NIP44.encrypt(channelKey[1], privKey, myPubkey)
       tags = [['d', dtag], ['p', myPubkey]]
  10. Опубликовать kind 30054 (allowlist) с владельцем как единственным разрешённым автором:
       d-tag = HMAC(masterSecret, "30054:" + channelId + ":1")
       content = ChaCha20-Poly1305(JSON({channelId, version:1, allowedAuthors:[myPubkey]}), channelKey[1], nonce)
       tags = [['d', dtag], ['channel', channelTopic]]

grantChannelAccess(channelId, readerPubkey, perms /* VIEW or VIEW|COMMENT */, privKey):
  1. v ← channelKeyMeta[channelId].currentVersion
  2. ck ← getChannelKey(channelId, v)
  3. Опубликовать kind 30053 для readerPubkey:
       d-tag = HMAC(masterSecret, "30053:" + channelId + ":" + readerPubkey + ":" + v)
       content = NIP44.encrypt(ck, privKey, readerPubkey)
       tags = [['d', dtag], ['p', readerPubkey]]
  4. Если perms содержит COMMENT:
       новый allowlist[v] ← старый ∪ {readerPubkey}
       Перевыпустить kind 30054 (тот же d-tag, новый content + новый created_at):
         content = ChaCha20-Poly1305(JSON({channelId, version:v, allowedAuthors:[...]}), ck, nonce)

revokeChannelAccess(channelId, revokedPubkey, privKey):
  1. v_new ← currentVersion + 1
  2. ck_new ← crypto.getRandomValues(32)
  3. channelKeyMeta[channelId].currentVersion ← v_new
  4. Сохранить channelKey[v_new]
  5. allowlist_new ← allowlist_current \ {revokedPubkey} (если был там)
  6. Для каждого оставшегося читателя R с VIEW:
     ekey ← NIP44.encrypt(ck_new, privKey, R)
     Опубликовать kind 30053 d-tag = HMAC(...:R:v_new), content=ekey, tags [['d',dtag],['p',R]]
  7. Для себя: то же на myPubkey
  8. Перевыпустить kind 30054[v_new]:
     d-tag = HMAC(...30054:channelId:v_new)
     content = ChaCha20-Poly1305(JSON({version:v_new, allowedAuthors: allowlist_new}), ck_new, nonce)
  // Старые kind 30053 для revokedPubkey остаются на relay (HMAC d-tag не пересекается),
  // но это не страшно: revokedPubkey может расшифровать только свои старые ключи.
  // Контент новых эпох недоступен.

createPost(channelId, text, privKey):
  1. v ← currentVersion
  2. ck ← getChannelKey(channelId, v)
  3. nonce ← crypto.getRandomValues(12)
  4. ct ← ChaCha20-Poly1305(text, ck, nonce)
  5. payload ← uint32BE(v) ‖ nonce ‖ ct
  6. Опубликовать kind 30061:
     tags = [['d', `${channelId}:${postId}`], ['channel', channelTopic]]
     content = base64(payload)

readPost(event):
  1. payload ← base64Decode(event.content)
  2. v ← uint32BE(payload[0..4])
  3. nonce ← payload[4..16]; ct ← payload[16..]
  4. ck ← getChannelKey(channelId(event), v)
  5. text ← ChaCha20-Poly1305.decrypt(ct, ck, nonce)

addComment(channelId, postId, parentId, text, privKey):
  // Доп. локальная проверка перед публикацией: я в allowlist[v]?
  1. v ← currentVersion
  2. allowlist ← commentAllowlists[channelId][v]
  3. Если myPubkey ∉ allowlist → отказать в UI (нет COMMENT)
  4. Иначе: создать kind 30062 аналогично createPost, с tags = [['d', postId+':'+commentId], ['channel', topic], ['e', postId], ['e', parentId]]
```

### 12.8. Удаление события (NIP-09)

```
deleteEvent(targetEventId, reason?, privKey):
  1. Опубликовать kind 5:
     tags = [['e', targetEventId]]
     content = reason || ''
  2. Применение на стороне получателя:
     a. Получить kind 5
     b. F-EV-08: проверить, что event.pubkey == автор targetEventId
     c. Записать в deletions
     d. fold: пометить материализованную запись deleted=true
     e. UI: показать «Сообщение удалено»
```

### 12.9. Lock/Unlock (защита локальной БД)

```
onIdle(24h) или explicit lock:
  1. Очистить из памяти: privKey, masterSecret, dbKey
  2. Перейти на экран unlock

onUnlock(password):
  1. Загрузить keystore: {salt, iv, ciphertext}
  2. PBKDF2 → AES-GCM decrypt → privKey
  3. Производство: masterSecret, dbKey
  4. Восстановить состояние из БД
  5. Подключиться к relay → AUTH (нужна повторная подпись 22242)
```

## 14. Ограничения и допущения

### 14.1. Ограничения

| ID   | Ограничение                                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L-01 | Потеря мнемоники = потеря аккаунта. Восстановление невозможно                                                                                                  |
| L-02 | Relay может удалить события. Для надёжности — несколько relay. State-snapshot: история не воспроизводится                                                      |
| L-03 | Без Double Ratchet (MVP) компрометация ключа раскрывает историю DM                                                                                             |
| L-04 | Права применяются клиентом. Защита — шифрование (без channelKey контент недоступен) + allowlist comment-авторов                                                |
| L-05 | Bootstrap зависит от доступности relay. Lazy-load зависит от доступности relay в момент открытия чата/канала                                                   |
| L-06 | Мнемоника BIP-39 + NIP-06 даёт совместимый формат ключа, но **не работу в публичной Nostr-экосистеме**                                                         |
| L-07 | Отзыв доступа: бывший читатель сохраняет доступ к контенту эпох ≤ v_revoke. Перешифрование архива — backlog 2.1                                                |
| L-08 | NIP-59 рандомизирует `created_at`. Используется Lamport из rumor                                                                                               |
| L-09 | NIP-17 удваивает исходящий трафик (gift wrap для получателя + для себя)                                                                                        |
| L-10 | Инвалидация кэша прав в MVP — полный пересчёт. > 10000 правил — заметно                                                                                        |
| L-11 | Редактирование комментариев не сохраняет историю правок                                                                                                        |
| L-12 | Lamport — singleton на пользователя. Для групповых чатов — backlog                                                                                             |
| L-13 | Файлы на Blossom живут до тех пор, пока сервер их хранит. Для критичных вложений — локальный backup                                                            |
| L-14 | Web Crypto API требует Secure Context. `file://` не поддерживается                                                                                             |
| L-15 | Деплой — пара `index.html` + `service-worker.js`                                                                                                               |
| L-16 | Расхождение часов между двумя устройствами одного пользователя > 60 секунд может приводить к LWW-аномалии. Митигация: F-RL-06 предупреждает при > 30с          |
| L-17 | Relay видит routing-метаданные (NIP-42 pubkey, `#p`/`#channel` теги, объёмы трафика, время онлайна) — см. § 1.3. Полное скрытие требует Tor/Mix-net (не в MVP) |
| L-18 | Federation между разными экземплярами Ugolok отсутствует (§ 1.2). Self-host = свой остров                                                                      |
| L-19 | Голосовые inline ограничены 32 KB raw (~5 секунд opus 50 kbps). Для длинных голосовых — Blossom                                                                |
| L-20 | Lock после 24 ч idle: пользователь должен ввести пароль повторно. Длинные оффлайн-сценарии прерываются                                                         |

### 16.2. Smoke-test NIP-44 round-trip

```javascript
import * as nip44 from "nostr-tools/nip44";

const aliceSk = schnorr.utils.randomPrivateKey();

	plaintext,
	nip44.v2.utils.getConversationKey(aliceSk, bobPk),
);
```

### 16.3. Smoke-test opaqueDTag

```javascript
import { hmac } from "@noble/hashes/hmac";
import { sha256 } from "@noble/hashes/sha256";
import { utf8ToBytes, bytesToHex } from "@noble/hashes/utils";

function opaqueDTag(masterSecret, kind, logicalKey) {
	const input = utf8ToBytes(`${kind}:${logicalKey}`);
	return bytesToHex(hmac(sha256, masterSecret, input));
}

const ms = new Uint8Array(32).fill(7);
const a = opaqueDTag(ms, 30051, "subjectA:resourceX");
const b = opaqueDTag(ms, 30051, "subjectA:resourceX");
const c = opaqueDTag(ms, 30051, "subjectB:resourceX");
console.assert(a === b); // детерминирован
console.assert(a !== c); // разный для разных входов
console.assert(a.length === 64); // 32 байта в hex
```

## 18. Что осознанно не входит в MVP

- Forward secrecy для DM (Double Ratchet).
- Групповые чаты.
- Модерация каналов (rate-limit, ban, отчёты).
- Discovery каналов.
- Поиск по истории.
- Уведомления (push, sound, badges).
- Темы оформления: одна светлая + одна тёмная, без кастомизации.
- Локализация: только русский и английский.
- Эмодзи-пикер, GIF, стикеры.
- Совместное редактирование, голосования, опросы.
- Мобильные приложения (Cordova/Capacitor) — только web.
- Federation между экземплярами Ugolok.
- Перешифрование архива канала при revoke (backward secrecy для бывших читателей).
- Tor / mix-net для скрытия routing-метаданных.
